# CoT Explain

[English](README.md) | **日本語** | [繁體中文](README.zh-TW.md)

> ドキュメント一つ——あるいは今しがた終えた会話——を指定すると、
> CoT（思考連鎖）Mermaid 図を中心に据えた自己完結型の HTML 解説ページを
> 生成します。各ノードが推論のひとステップ、各矢印には「なぜそのステップが
> 導かれるのか」を示すラベルが必ず付きます。

---

## このスキルがすること

長いドキュメントの中に埋もれた推論や、あなたしか居合わせなかった会話の
中の推論は、他の人には存在しないのと同じです。このスキルはそれを可視化
します。

ソースを読み、実際の推論連鎖——どんな主張があり、それぞれ何に支えられ、
隣り合う主張がどう繋がるのか——を抽出して、一つの HTML に描き出します。

1. 一行の結論
2. CoT Mermaid 図（本体）
3. ノードごとの展開：主張 / 根拠 / このステップで何が変わったか
4. 検討したが却下した選択肢と、その理由
5. この連鎖が前提にしていること、まだ答えの出ていない問い

**ワンショットの生成器**です。データベースには何も書かず、セッションを
またいだ追跡もしません。実行して、ページが出て、終わりです。

---

## 図の記法規約

汎用の Mermaid ではなく、固定されたハウススタイルに従います。

```
graph TB
subgraph r1["段階の見出し"]
direction LR
  A["<div style='text-align:left'>前提<br/>━━━━━━<br/>• 箇条書き一<br/>• 箇条書き二<br/>• 箇条書き三</div>"]
  B[...]
  C[...]
end
A -->|判断の土台を形成| B
B ==>|集約して| C
style A fill:#f8f9fa,stroke:#868e96,stroke-width:2px
```

- 各ノード：見出し、`━━━━━━` の区切り線、三〜五つの箇条書き、左揃え
- **すべての**矢印が関係を示すラベルを持つ——ラベルなしの矢印は省略では
  なく欠陥として扱う
- 矢印は三種類：`-->` 通常の導出、`-.->` 背景・弱い関連、`==>` 結論へ
  至る決定的なステップ
- ノードの色が役割を表す：前提・根拠・障害・試行・転換点・結論

**レイアウトは推測ではなく実測で決めています。**推論の連鎖は細長く、素の
`graph LR` では 3061 × 227 px——13.5:1 となりページ上で読めません。
mermaid-cli で 15 通りをレンダリングし SVG の viewBox で計測した結果、
仕様が現在強制している形が勝ちました：外側 `graph TB`、各行はそれぞれ
`direction LR` を宣言した `subgraph`、1 行あたり最大 3 ノード、箇条書きは
短く——**1022 × 824 px、正方形度 0.81**。効いているのは `direction` の
1 行です：subgraph があっても宣言がなければ 0.14 にしかなりません。
`nodeSpacing`／`rankSpacing` の調整は 13.48:1 を 13.39:1 に動かすだけで、
行き止まりです。箇条書きの数もレイアウトのレバーであり、しかも有利な方向に
働きます——図は横長なので 1 行増えるごとに縦が伸び、正方形へ近づきます
（3 つで 0.81、5 つで 0.95）。範囲を 3 固定ではなく 3〜5 としたのはこの
ためです。

**文字数の制限は警告であって失敗ではありません。**ノード幅は図中で最も
長い箇条書き 1 行が決めるため、ゲートが指摘するのはその 1 行だけで、
ビルドを止めることはありません。厳格な文字数上限は、数字を満たすために
文章を壊すことを著者に強いるもので、少し広い箱より悪い結果になります。

このレイアウトは vault 自身の慣例（`graph LR`、`subgraph` 不使用）から
意図的に外れています——あちらは短い連鎖ばかりで、13:1 が問題にならない
ためです。計測表を含む完全な仕様は `references/mermaid-cot-spec.md` に。

## 出力

**markdown が成果物であり、HTML はそこから導出されます。** `.md` には
vault のノート標準に沿った Obsidian 互換の frontmatter が付くので、残す価値
のあるページはそのまま vault へ移せます。HTML は `render_cot_html.py` が
機械的に生成します——パーサは markdown-it-py、このリポジトリの既存
markdown レンダラと同じライブラリです——そして手で編集することはありません。

どちらも `${TMPDIR:-/tmp}/cot-explain/` に置かれます。**意図的に一時領域**
です：この種のページはたいてい一度読んで終わりだからです。残したい場合は
`.md` を vault へ移すか、HTML を Artifact（claude.ai 上の非公開ページ。
あとから共有するか選べます）として公開してください。公開は一度だけ確認し、
内容のアップロードを伴うため勝手には行いません。ローカル HTML は CDN から
`mermaid.js` を読むため、初回表示時にネットワークが必要です。

コンバータは「同種のレンダラが五日間で五回、静かに失敗した」ブリーフから
三つの性質を借りています：markdown が変換されずに残った場合は**大声で失敗し
何も書かない**、**その検査に範囲を限定する**（mermaid ブロックやコードスパンに
`|` や `**` があるのは正当）、そして**実際に動いたコピーのバージョンを全ページ
に刻印する**。

## 忠実性 — ゲートが検査できない領域

検証スクリプトはページが整形式であることを証明できますが、**ソースを忠実に表しているかは証明できません**。機械的な手段では原理的に不可能です——すべてのノードの形が正しく、すべての矢印にラベルがあってなお、読者がソースの否定した結論を持ち帰ることがあり得ます。

仮定の話ではありません。実際の英語ソースで round-trip テストを行ったところ、読者は解決策を「特定のパスに固定する」ことだと理解しました。しかしソースは固定パスが機能しない理由を導出したうえで、**自己位置解決ルール**を指定していました——その通りに実装すれば、否定されたはずの案が出来上がります。判定はこうです：「なぜ」の記述としては忠実、「何をするか」の記述としては使用不能。

そこで本スキルは **Step 6 忠実性チェック**を備え、その場にいなかった人にページを渡す前に実行します。simulatability 型の round-trip（forward simulation, Doshi-Velez & Kim 2017／Leakage-Adjusted Simulatability, Hase et al. 2020）で、三巡します：一つ目のエージェントはページのみから推論を再構成する。二つ目はソースとその再構成だけを読み、**ページは決して見ずに**誤解と欠落を判定する。三巡目は逆方向 — 図の中にソースに存在しないものが紛れていないかを確かめる。

**このページがしないこと。** ソースが**実行されるための文書**——ただ読まれる
のではなく、それに従って行動されるために書かれたもの——である場合、このページは
それがなぜそう決めたのかを説明します。**原典の代わりにはなりません。** 技術仕様書
は最も分かりやすい一例で、規程・契約・臨床プロトコル・法令・スタイルガイドにも同じ条件が適用されます。 この限界は実測です：密度の高い一つの技術
ブリーフに対して四巡しましたが、各巡は前巡で指摘された条項をすべて回収し、
そのたびに誰も探そうとしなかった別の実装詳細を落としました——新規の欠落は
1 件、2 件、3 件。探索カテゴリを追加しても、損失は終わるのではなく場所を
変えるだけでした。メカニズムを示すノードの逐語引用は差を縮めます
が、閉じはしません。だからソースが実行されるための文書のときは、ページ自身が
そう明記します。

このページ本来の役割は四巡すべてで無傷でした——覆された判断、理由付きで却下
された選択肢、条件付きの撤退——そして直近三巡の幻覚チェックは何一つ捏造を
検出しませんでした。

そこから導かれた修正は、意図的に小さく留めてあります。ノードカードに追加したのは一つの項目だけ —— `例外／失効条件`、すなわち Toulmin の *rebuttal* です。「この主張はどの範囲でのみ成立するか」こそ、要約が最も失いやすく、失うと最も害の大きいものだからです。図の語彙は一切変えていません。背後にある規則はこうです：**書き写して埋める欄は追加してよい、判断して埋める欄は追加しない。** 「ソースはどんな限定を述べたか」への答えは読者間で一致しますが、「この主張はどれだけ確からしいか」への答えは一致しません。

## 近接スキルとの使い分け

| 状況 | 使うもの |
|---|---|
| すでにある推論を人に説明する共有可能なページが欲しい | このスキル |
| まだ考えている最中。セッションを跨ぎ、前提を追跡したい | `think-orbit:thinking-session` |
| 過去の推論が依拠していた前提が崩れた | `think-orbit:break-assumption` |
| 会話の途中で見失い、チャット内で再定位したい | `dev-workflow:recap-state` |
| セッション状態を未来のコールドリーダー AI に引き継ぐ | `dev-workflow:handoff` |
| CoT ハウススタイル不要の、任意の Mermaid 図 | `obsidian:obsidian-mermaid-visualizer` |

最も重要な線引き：**think-orbit は「考える」ため、こちらは「すでに考えた
ことを説明する」ため。**両者は併存します。

## 起動フレーズの例

- 「このドキュメントの思考の流れを図にして」
- 「この会話がどう導かれたか説明して」
- 「CoT の解説ドキュメントを作って」
- 「`docs/spec.md` の推論連鎖を描いて」
- "explain this as a CoT diagram"
- "make an HTML explainer for this"

---

## 拒否すること

- **ソースを読まずに図だけ描く**。推論の抽出こそが仕事であり、ファイル名
  から推測した図は創作です。
- **ノード数を満たすための水増し**。実際の推論が 5 ステップに満たなければ
  そう告げ、代わりに散文を提案します。
- **却下された選択肢の捏造**。ソースが代替案を検討していなければ、その節は
  埋めるのではなく削除します。

## ファイル構成

```
cot-explain/
├── README.md           <- English
├── README.ja.md        <- 日本語（本ファイル）
├── README.zh-TW.md     <- 繁體中文
├── SKILL.md            <- 操作ファイル（Claude 用）
├── assets/
│   └── cot-report-template.md    <- 成果物テンプレート（markdown）
├── references/
│   └── mermaid-cot-spec.md       <- 図の構文 + 内容の契約
└── scripts/
    ├── render_cot_html.py        <- markdown → HTML（markdown-it-py）。失敗時は何も書かない
    └── verify_cot_html.py        <- ゲート：FAIL は停止（exit 1）、WARN は助言。--render で実パーサ検証
```
