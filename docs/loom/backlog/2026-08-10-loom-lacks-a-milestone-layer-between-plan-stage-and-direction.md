- Start: next time a repo (this one or external) needs to answer "how far along is deliverable X" where X spans ≥2 plans — or the first design session on the progress model after the ship-progress-tooling arc merges
- Origin: 2026-08-10 kumiko-zaiku-app-icons session 63262433 — the repo hand-maintains a progress.md tracking M1 Parts 1-5 across multiple plans; it drifted from reality four times, each drift surviving every gate because no gate recognizes a hand-copy; the session's own diagnosis ("a hand-copy standing in for the layer loom lacks") was verified against this repo the same day: plan_card.py covers per-plan state only, backlog_index.py covers cross-plan queue/direction only, and no artifact covers milestone-of-one-deliverable

- What: loom's progress surfaces are two-layered. Bottom: a plan file's
  `Stage:` + per-task `Status:`, machine-flipped and machine-rendered by
  plan_card.py — scope is ONE plan. Top: `DIRECTION.md` (`## Now` /
  `## Next` bets) + `BACKLOG.md`, generated by backlog_index.py — scope
  is the whole repo's queue. Neither answers the question a
  multi-plan deliverable poses: "M1 has five parts across five briefs;
  which parts are shipped, which is in flight, which are unstarted?"

  kumiko answered it by hand-inventing `progress.md` — a table mapping
  Parts 1-5 to their shipped/pending state. It drifted four times
  (three shipped PRs missing, one Part still marked 待收分支 after its
  PR merged); a fourth-drift fix in session 63262433 predicted the
  fifth. The mechanism: no generator writes it, no gate validates it,
  so every close-out that forgets it leaves a lie that reads as truth.

  The design question is NOT "ship the table" but which existing
  surface grows the milestone dimension: (a) DIRECTION.md bets gain a
  parts-checklist sub-structure that backlog_index.py can regenerate
  from plan ledgers; (b) multi-part briefs (the `<topic>-part-N.md`
  convention writing-plans already defines) get an index artifact
  generated from their plans' Stage/Status lines; (c) nothing new —
  declare per-plan Stage + DIRECTION.md sufficient and document that a
  hand-kept roadmap table is an anti-pattern. Option (c) is cheapest
  and may be right: the kumiko table's value was real but its cost was
  four silent lies. Whichever way, the decision should cite the
  ship-progress-tooling arc's outcome — once plan_card.py actually
  arrives in external repos, per-plan cards may cover most of the need.

  Related: docs/loom/DIRECTION.md (direction layer, PR#677),
  docs/loom/specs/2026-08-10-ship-progress-tooling.md (the delivery
  half of the same observation).

- 2026-08-21 note: option (a) is foreclosed by
  docs/loom/plans/2026-08-21-dissolve-direction-layer.md — `DIRECTION.md`
  no longer exists, so a bets-grow-a-parts-checklist sub-structure has
  no document to grow inside. The remaining options are (b) a
  multi-part-brief index artifact and (c) declare per-plan Stage +
  the live `--ready` queue sufficient. This entry stays open with
  its option set narrowed to those two. (Corrected 2026-08-21 during
  the same arc's round-4 review: this note as first written offered
  the generated `## Now` view, which that arc deleted — the note
  recording what the dissolution foreclosed had itself named a
  foreclosed surface.)
