# 畢業探針不得依賴本機分支歷史 — 我試了什麼、發生了什麼

2026-09-05 在一份乾淨的專案副本上試的，版本號前七碼 `294d85ea`。

這次是第一波（wave-end:1）的檢查點：新命令跟刪測試這兩件事已經做完，但「build 站的文字要求先跑這命令」跟「版本號加一」還沒做（在下一波）。所以第 3、4 條有一部分現在還試不了，下面會分別說明能試到哪裡。

## 你要的東西，一條一條試

### 1. 在任一分支下一個命令，它自己建出像 CI 的乾淨副本跑畢業探針，列出每支失敗與每支跳過的理由；本機綠、副本紅時結束碼非 0，全綠結束碼 0

- **我怎麼試的**：先看這個新命令的說明（`--help`），再直接在乾淨副本上跑一次真正的命令（跑了全部畢業探針，385 支）。接著另外搭了兩個一次性的小型測試專案，專門用來驗證「結束碼」這件事：
  - 專案 A：只放一支故意讀「本機才有的 main 分支」的假探針，直接跑這個命令。
  - 把同一支假探針改寫成「先試遠端的 main、都沒有才跳過」，再跑一次。
  - 專案 B：完全沒有遠端 main 這種東西的情況下再跑一次，確認「跳過」這條路徑本身也會被列出來、理由也讀得到。
- **發生了什麼**：
  - 在真正的專案上，命令印出一行「這次排練的版本號是哪一個、副本放在哪裡」，然後是失敗清單（這次是 0 支）、跳過清單（1 支，理由是一個已知的、跟本機分支歷史無關的文字判讀邊界案例，不是「歷史讀不到」那一類），最後印出 384 通過、1 支已知失敗但預期內、跳過 1 支，結束碼 0。
  - 在專案 A（假探針讀本機 main）：命令印出這支測試在「失敗」清單裡，附上具體錯誤（讀不到 main，因為乾淨副本本來就沒有本機的 main），結束碼是 1（非 0）。
  - 改寫成先試遠端 main、都沒有才跳過之後：命令印出 0 失敗、通過 1 支，結束碼 0。
  - 專案 B（連遠端 main 都沒有）：命令印出這支測試在「跳過」清單裡，附上跳過的理由（「遠端與本機的 main 都讀不到」），結束碼仍是 0——跳過不會讓命令變紅。
- **證據**：三次命令的完整終端輸出（結束碼分別為 0、1、0、0）；假探針的原始版本與改寫版本（原始版本在本機工作目錄裡單獨跑是綠的，這正是問題所在——本機綠不代表乾淨副本綠）。
- **結論**：做到了。

### 2. 用一支故意讀本機 main 的合成探針試它：命令要紅；把探針改成先讀遠端 main、都沒有就跳過，命令要綠

- **我怎麼試的**：同上一條的專案 A——這條驗證的正是同一組操作，這裡把它單獨列出來對照。
- **發生了什麼**：讀本機 main 的版本在乾淨副本裡讀不到，命令回報失敗、結束碼 1；改寫成先讀遠端 main、都沒有才跳過的版本，命令回報通過、結束碼 0。
- **證據**：與第 1 條相同的兩段終端輸出。
- **結論**：做到了。

### 3. build 站的記憶步驟文字寫明「畢業前跑這命令，紅的不得畢業」，且有測試釘住那句話

- **我怎麼試的**：打開 build 站現在的文字，找「畢業」那一段，看有沒有提到這個新命令。
- **發生了什麼**：目前那一段只講「把探針複製進永久測試目錄」，完全沒有提到要先跑這個命令、也沒有講紅了不能畢業。這件事排在下一波（版本號、站文字都還沒動）。
- **證據**：讀了 build 站文字裡「畢業」那一段的現況，裡面沒有這命令的名字。
- **結論**：現在還試不了——這是下一波要做的事，不是這一波漏做。

### 4. 這個 change 合併後，在 main 上跑這命令：0 失敗，且跳過理由裡沒有「commit 不在歷史」「change 已 shipped」這兩類

- **我怎麼試的**：在乾淨副本（也就是這個分支目前的樣子，還沒合併）上直接跑了一次完整命令，檢查失敗清單跟跳過清單的每一句理由。另外確認了以前那兩類「必定跳過」的測試程式碼是不是真的不見了。
- **發生了什麼**：0 支失敗。跳過清單只有 1 支，理由是前面提過的文字判讀邊界案例，跟「歷史讀不到」「commit 不在」「已經 shipped」這些完全無關。原本那兩類——一類是讀某個已經被壓縮合併、本機才找得到的 commit，一類是讀某個 change 是否已經出貨的分支狀態——對應的程式碼已經不在測試檔裡了。
- **證據**：完整命令的終端輸出（385 支裡 0 失敗、1 支跳過、理由已貼在上面第 1 條）；在測試檔裡搜尋舊有兩個判斷函式的名字，沒有找到。
- **結論**：以現在的分支狀態（尚未合併）試，結果符合要求；等真正合併到 main 之後，還需要在 main 上再跑一次做最終確認——這件事排在關閉這個 change 的那一步，不是現在能做的。

## 對你既有的資料做了什麼

沒有——這個 change 不會動到你已經有的任何東西。這個新命令只會在系統的暫存資料夾裡建一份完整專案的乾淨副本來跑測試，跑完就把那份副本收掉；你的工作目錄本身只被讀取，不會被寫入。刪掉的那幾支測試是版本控制內的測試檔案，仍然能從歷史紀錄裡找回來。

## 我幫你決定的事

- **乾淨副本要「完整歷史、有遠端 main、沒有本機 main」這個形狀，而不是更嚴格的淺層副本** — 因為這正是你們的自動化檢查在真正跑的形狀；改用更嚴格的形狀不在這次的範圍內，之後想測那個形狀要另外開一次改動。
- **命令的結束碼只看失敗、不看跳過** — 我判斷跳過是「值得你自己讀一下理由」的資訊，而不是自動判定失敗，理由是這次要抓的問題本來就是「探針靠不住的東西」，跳過就是探針老實承認靠不住，跟测试真的紅了不是同一件事。如果之後發現這個判斷太寬鬆（跳過的東西其實根本沒被驗證到），可以改成讓某些跳過也算紅。
- **原本三次事故裡累積的舊測試，選擇刪掉而不是改寫成新形式** — 因為它們本來就只驗證「本機才有的東西」，改寫等於重寫；被刪的測試名稱跟被刪的理由都寫在那次改動的紀錄裡，可以核對。
- 到目前為止，沒有任何審查意見被判定為「重要以上但不處理」——這個檢查點的審查記錄還沒有收到具體意見。

## 你可能還沒想清楚的地方

- 這個新命令目前只是「文字上要求跑」，不是強制擋下推送的機制——如果下一次改動又在真正的自動化檢查裡出現紅字，那就代表光靠文字提醒不夠，得考慮把它做成真正擋得住人的機制。
- 第 3、4 條要等下一波（文字加上去、版本號加一、合併到 main 之後）才能完整驗收；這份報告目前只能證明「命令本身做得對」，還不能證明「大家真的會照著做」。
