## 你要的東西，一條一條試

- **證據**：`-X importtime` 輸出中無 `yaml` 字樣，也無「印錯誤堆疊」用的那個模組字樣；推送情境下既有測試檔 `test_loom_checker_push.py` 173 項全過；新增的模擬「規則設定檔解析工具根本沒安裝」情境測試 3 項全過。
- 這條累計修了兩處：一是「規則設定檔解析工具沒裝」這種極端情況下的失敗方式改回跟改動前一模一樣；二是這次又把原本用來印那種失敗訊息的輔助模組也從平常操作路徑上拿掉,平常操作不再多載這個模組。兩處都重新試跑確認過了。

### 2. 引用檢查：在本 repo 對全部 markdown 跑檢查程式，改前與改後的畫面輸出、錯誤輸出、結束代碼要逐字一樣；牆上時間從 1.2 秒以上降到 0.6 秒以下（原定 0.4 秒是規劃階段用剖析工具推估的數字，你在看過實測 1.77 秒→0.57 秒、運算時間 0.56 秒之後核可改成 0.6 秒；剩下的時間是開 3,383 個檔案與比對本身，不在這次要消除白工的範圍內）；三種刁鑽引用情境改前改後輸出要逐位元相同
- **怎麼試的**：對本專案全部說明文件跑一次引用檢查，改動前後各跑一次，逐字比對輸出與結束代碼；再各量測三次耗時。另外用三種刁鑽情況（兩個資料夾各放一份同名檔案；引用一個帶斜線但根本不存在的路徑；引用一個裸檔名但根本不存在）分別造出小型測試環境，改動前後各跑一次比對輸出。
- **發生了什麼**：全專案跑法下三種刁鑽情況輸出完全一致。全專案的完整輸出比對這次多一道手續才能公平：這台副本除了效能改動之外,期間還累積了其他跟這次改動無關的文件更新（例如更新紀錄檔案本身被改寫,行號因此跟著挪動),直接拿改動前的版本去跟改動後的版本比對輸出,會看到一些「行號不一樣」的差異,但那是文件本身內容變了,不是檢查程式的答案變了。改用公平的比法——同一份文件內容,分別餵給改動前的程式和改動後的程式——輸出一字不差。耗時方面，改動後三次落在約 0.86-1.04 秒（其中程式實際占用的運算時間約 0.78-0.80 秒），改動前三次落在約 2.30-3.52 秒（運算時間約 2.05-2.40 秒）。量測當時這台機器背景負載很高（`uptime` 顯示 1 分鐘平均負載超過 200，跟其他人同時在跑東西有關),牆上時間會被排隊等候拉長,所以這次改用「程式實際占用的運算時間」當主要依據，牆上時間僅供參考；即使用運算時間看，也沒有壓到原定的 0.4 秒以下（那是改門檻前的數字；核可後的門檻是 0.6 秒）。另外在一台當下比較安靜的機器上量到的數字是改動後約 0.57 秒、改動前約 1.77 秒,可以佐證這台機器的偏高背景負載確實墊高了兩邊的絕對秒數,但沒有改變「快了三倍、較安靜機器上的 0.57 秒符合 0.6 秒目標」這個結論。剩下的時間大部分花在把三千四百多份文件的內容讀進來、在裡面搜尋文字,這件事這次改動一開始就沒打算去動。

## 我替你決定的事

- **第 5 條的目標數字被下修**——原本設想「驗證跟更新這兩個動作,票只被讀一次」,但實際量到「更新」動作因為內部還會再呼叫一次「驗證」,做不到只讀一次,只能做到「讀兩次再加一次」而不是原本更沒效率的「讀四次再加一次」。這個下修是在動手實作之前就先跟你對過並寫進計畫,不是事後補救;如果你原本期待的是真正只讀一次,現在的結果離那個更遠一步的優化還有距離。
- **第 4 條保留了一個原本就存在的小毛病**——如果一張票的「檔名」本身含有非英文字元（例如日文),從歷史紀錄讀取時會被悄悄跳過、不會出現在結果裡。你要求這次改動「看得見的行為一個位元組都不能變」,所以這個毛病被刻意原封不動地留著,會另外排一次改動去修。如果你的地圖裡剛好有這種檔名的票,你會發現它們在讀歷史時被漏掉——這不是這次改動造成的,是本來就有的。
- **第 2 條的加速查找機制留了一個已知但接受的小縫隙**——如果有人在第一次查找之後,原地把同一份檔案清單的內容整批換掉（清單長度不變、但內容變了）,加速查找機制不會發現清單已經換過,可能給出過時的答案。目前程式裡沒有任何呼叫方會這樣做,這個縫隙已經被寫成「這份清單一旦用來查找就不能再原地改內容」的使用規則,而不是花更多成本在執行時逐一檢查每個內容有沒有變。
- **第 2 條的目標秒數,你被問過之後選擇接受目前量到的速度,而不是要求進一步去改動比對文字的邏輯本身**——原本規劃階段的 0.4 秒只是粗估;你看過實測數字（1.77 秒降到 0.57 秒）之後,決定就以這個速度為準,不再要求把剩下花在讀檔與比對文字上的時間也一併壓縮。
- 目前為止沒有任何「重要或更嚴重」等級的問題被看過又刻意放行不修——沒有這類項目需要跟你交代。

## 你可能還沒想清楚要不要的事

- 第 2 條的秒數是在一台當下負載偏重的機器上量的,兩邊倍率關係看起來穩定,但如果你在意的是絕對秒數要壓在 0.4 秒以下,可能需要在一台空閒的機器上重新量一次才能下定論。
