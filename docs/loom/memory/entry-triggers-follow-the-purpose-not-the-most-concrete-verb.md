description: When a plugin's entry vocabulary is written from the most concrete verb in its design ("decide"), the trigger becomes narrower than the product's purpose ("think and plan") and the first real user cannot get in the door with their natural phrasing — write trigger phrases from the purpose statement the user actually gave, then list the concrete verbs as instances
type: practice
origin: think-orbit 0.1.1 (2026-08-18) — the user, about to run the Part 1 real-material checkpoint, said 「我要決定 X 這個啟動方式好像太窄了 原始目的應該是 思考 與 規劃」; the router and core skill had been named and triggered around "決定/decide" although the brief's job story and the plugin name (think-orbit) were about thinking; fixed by renaming decision-session → thinking-session, widening descriptions (幫我想／規劃／整理思路／think through／plan), and stating that a sitting need not end in a DECISION
---

The plugin's design note used "決策" as its running example, and every
entry surface — skill name, description triggers, the first question the
agent asks — inherited that word. The user's own purpose statement, one
line earlier in the brief, was wider: think through and plan.

**Why:** entry vocabulary is the only part of a plugin the user meets
before the protocol runs; if it names one concrete outcome, users with
the same job but a different framing bounce, and the checkpoint measures
the door instead of the room. The concrete verb also leaks into
semantics — "GOAL = what to decide", "the sitting ends in a DECISION" —
which then read as mandatory.

**How to apply:** when writing a router/entry description, start from
the user's purpose sentence in the brief (job story), not from the design
note's worked example; list the concrete verbs (decide, choose, plan,
figure out) as instances under it; and check the core protocol's first
question and success criteria do not silently require the concrete
outcome. Re-read the plugin's own name — it usually already says the
purpose.
