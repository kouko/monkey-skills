---
name: a-name-grep-cannot-see-a-rename-written-as-prose
description: A rename sweep anchored on `name(:|/)` misses every prose occurrence — "a loom-spec change-folder", "the loom-discovery station" — and the sweep reports clean while stale names remain in live assertions and cross-file section references; anchor the separator class to include prose, and treat a clean grep as necessary, never sufficient
type: gotcha
origin: loom-design-merge (6 plugins → 2 consolidation, parts 1-3, 2026-08-16/17)
---

The inventory grep for the 6→2 plugin rename was:

```
loom-(discovery|product-principles|interface-design|spec|pipeline)(:|/)
```

It catches `loom-spec:spec-expansion` and `loom-spec/scripts/foo.py`. It
catches nothing written as English:

```
a validated loom-spec change-folder
generated by the loom-discovery station
§Consuming a loom-spec change-folder     <- a cross-file SECTION reference
```

The sweep went green. The full pytest run then failed on
`test_spec_to_code_wiring.py`, which asserted the literal section heading
`"Consuming a loom-spec change-folder"` — the heading had been renamed to
`loom-design`, and the assertion string was invisible to a separator-anchored
grep because it sits inside `assert '...' in text`. A later prose-form sweep
found 115 more occurrences across 51 files.

**The widened pattern** (the trailing class is what matters):

```
(^|[^a-z-])loom-(spec|pipeline|discovery|interface-design|product-principles)[ `.,)]
```

The leading `(^|[^a-z-])` is equally load-bearing in the other direction: it
excludes deliberately-kept names that CONTAIN a retired one as a substring —
here the member skill `using-loom-pipeline`, the asset `loom-pipeline.js`,
and the workflow file `loom-pipeline-ci.yml`, none of which were renamed. A
sweep without it produces false positives that an agent will "fix" into real
breakage.

**But that exclusion cuts a THIRD blind spot, and this one bit too.** The
`-` inside `[^a-z-]` also excludes every RETIRED name that carries a
hyphenated prefix. `using-loom-spec`, `using-loom-interface-design`,
`using-loom-product-principles`, and `using-loom-discovery` were four
deleted router skills — and the widened sweep above could not see a single
one of them, for exactly the same reason it correctly hid
`using-loom-pipeline`. A whole-branch review found
the survivors clustered precisely where that form lives: a routing table row
still telling readers to reach for three deleted skills, a README titled
with the retired plugin name (a BARE name, no separator at all), and a
skill description gating on "the four station plugins" after the merge made
it two.

So the exclusion needs an allow-list, not a character class: sweep
`[a-z-]*loom-(retired names)` across live surfaces and allow-list the
handful of deliberately-kept component names by exact string. A character
class cannot distinguish "kept on purpose" from "deleted, prefixed" —
only an enumeration can.

**Classify before editing.** Three buckets, and only two get touched:
assertion strings and live prose get re-pointed; genuinely historical
statements — `originally §…` provenance lines, dated experiment reports,
verbatim quotes of untouched decision docs — stay. Getting this wrong in
either direction is a defect: editing history falsifies the record, and
skipping a live pointer leaves a reference that resolves to nothing.

**A rename can also kill a test without touching it.** The sharpest instance
in this arc was found by neither grep nor the suite:
`scripts/test_check_version_bump.py` fed the gate a path under the deleted
`loom-pipeline/`. The gate early-continues on any path whose plugin is not
in `CODEX_ELIGIBLE`, so after the merge that input never reached the
test-file-skip branch the test exists to guard. It stayed green — and stayed
green with the guarded logic deleted. Nothing was stale: the string was
correct when written, and deleting a directory elsewhere made it
unreachable. A retired name inside a FIXTURE is not a cosmetic leftover; it
can silently vacate the assertion. When a rename deletes a directory, grep
the suite for the old path as fixture INPUT, and prove each survivor still
fails under mutation — a green test is not evidence that it can fail.

**A qualified identifier inside a data file is neither prose nor a path.**
The last survivor in this arc was `docs/loom/firing-corpus/*.jsonl` — 28
records whose `"expected"` field named retired plugins
(`loom-spec:spec-expansion`, `loom-pipeline:loom-memory`). That corpus is the
GRADING ORACLE for skill-firing evaluation, and the harness derives a
skill's family from the prefix before the colon. So a *correct* fire of
`loom-design:spec-expansion` graded neither EXACT nor FAMILY — it graded
MISS. The oracle inverted: it would report the merged family as broken
precisely when it worked.

Every sweep was structurally blind to it. A path sweep cannot `test -e` a
qualified id (it is not a path). A prose sweep surfaces the file but reads it
as data, not as a pointer. And the corpus's own guard test asserted only
`expected == "NONE" or ":" in expected` — a retired plugin id satisfies that
perfectly, so 2514 green tests coexisted with a broken oracle.

The fix that generalizes is not the re-point; it is strengthening the guard
from SHAPE to RESOLVABILITY: assert each id resolves to a skill the repo
actually ships, derived from the manifests on disk. A shape check cannot
notice a rename; a resolvability check cannot miss one.

**Then the risk moves from the check's VALUES to the check's EXTENT.** Two
instances landed in the same round, and they are the same defect: a check
that is correct on what it looks at, reports green, and reads as covering
its whole domain.

- The strengthened corpus guard iterated a hard-coded tuple of three
  filenames. A fourth corpus shipped alongside them, validated by nothing —
  a deliberately bogus skill id in it passed the entire suite. Fix: enumerate
  the directory (`corpus_dir.glob("*.jsonl")`) and assert a floor on the
  count. That is the same fix shape as replacing a hand-maintained skill list
  with manifest enumeration, applied one level up.
- The path sweep reported "0 broken" while never deciding backticked
  repo-relative paths whose first segment is a retired plugin directory. The
  number was true of the predicate and false of the domain.

**Two rules worth carrying forward.** A completeness check must assert its
own extent — enumerate the members rather than list them, or it under-covers
silently the moment one is added. And a "0 findings" report is only as strong
as its decidability predicate, so state the predicate in the report: "0
broken" means nothing until a reader knows what was decidable.

**The generalizable rule.** A clean rename grep is a necessary condition, not
a sufficient one. The suite is the gate — it is what catches the prose form,
the assertion literal, and the cross-file section reference alike. And a
green suite is not sufficient either, when the rename removed the ground a
test was standing on. Related:
[[a-directory-move-shifts-every-relative-path-derivation]] (the sibling class
a name-grep cannot see at all).
