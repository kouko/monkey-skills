# W1 — L2 end-to-end harness (DuckDB fixture)

Source: `docs/dbt-wiki-quality-campaign.md` Phase 1, item W1.

## Design-side on-ramp

Axis 0 checked against the loom family on-ramp table: no `docs/loom/PRINCIPLES.md`
in this repo, no `DESIGN.md`/`ui-flows.md` for dbt-wiki, no existing spec/change-folder
for this item — but this is internal dev-tooling for an existing plugin (a
measurement harness, not a new product or user-facing UI surface), and the
campaign doc itself already serves as the scoping artifact. Rows 1-3 judged
not to fire (no product idea, no UI surface, no multi-state user-facing
behavior). Not surfaced to user as a detour option; proceeding directly.

## Problem

(Axis 1) dbt-wiki's core claim — "for ANY dbt project, `pack` produces a skill
that effectively answers business questions with executable SQL" — is
currently validated only by manual, private, single-project dogfooding (11
rounds, per the Journal). That signal is subjective, not reproducible, and
doesn't scale to catch regressions as dbt-wiki changes. The job: turn "does
this change help or hurt SQL-answering accuracy" into a question a machine
can answer, so campaign iteration (session or nightly) has an objective
target instead of a vibe check.

## Users

(Axis 2) Primary: the campaign's own iteration loop (this agent, future
sessions, eventually the Phase-4 nightly loop) — needs a pass/fail or scored
signal after each dbt-wiki change. Secondary: kouko, merging weekly batches —
wants a report, not a transcript re-read, to decide if a batch is safe to
merge.

## Smallest End State

(Axis 3) Already tightly scoped by the campaign doc and the Phase 3 backlog
(which explicitly defers scale-out to G1/G2/G3):
- One synthetic dbt-duckdb project at `dbt-wiki/tests/fixtures/`, ~10 models,
  seeded data, single dialect (duckdb), single language, mixed comment
  density, with 5 named guardrail traps (AVG-of-pre-aggregated-ratio,
  compound-key fan-out join, categorical `accepted_values` domain,
  forward-dated MAX(date) amortization trap, prefixed regional-twin
  scope-undercount).
- `gold-questions.yml`: question → exact expected number (derivable from seed
  data) + required invariants.
- A runner that drives a **real** headless Claude Code instance (`claude -p`,
  confirmed as the officially-supported non-interactive CI mechanism) through
  `/dbt-wiki:init` → `/dbt-wiki:pack` → answering each gold question against
  the packed skill + the fixture's DuckDB file, blind (no hints beyond what
  `pack` emits).
- A grader that compares the agent's numeric answers to `gold-questions.yml`
  and checks the stated invariants.
- This session also executes one real end-to-end run (confirmed with user:
  subscription quota, not metered API billing, so cost is not the blocking
  concern) to validate the harness actually works, not just that it parses.

Not smaller: the guardrail traps are the point — a fixture without them
would validate that a naive project passes, not that dbt-wiki's known failure
modes (per Phase 2 backlog) are actually caught. Removing them defeats W1's
purpose per the campaign doc.

## Current State Evidence

- **Forward**: no `dbt-wiki/tests/` directory exists yet (`find` confirmed).
  `init`/`pack`/`query` are conversational Skills invoked as
  `/dbt-wiki:init` etc. inside a Claude session (`dbt-wiki/skills/init/SKILL.md:1-10`,
  `dbt-wiki/skills/pack/SKILL.md:1-20`) — not standalone CLI scripts. The
  runner therefore must drive an actual Claude instance (headless), not just
  shell out to a python entrypoint.
- **Reverse**: `pack` reads from the same `.dbt-wiki/` location `init` wrote
  to (git repo root, `WIKI_DIR` resolution logic duplicated in both SKILL.md
  files) — the fixture project must be its own git repo (or the runner must
  isolate `WIKI_DIR` per run) so parallel/repeat runs don't collide.
- **Error**: `pack`'s governance section (`dbt-wiki/skills/pack/SKILL.md`
  Governance) hard-forbids committing a *real* emitted bundle into this
  public repo — not a concern here since fixture data is synthetic by
  design, but the runner must emit the fixture's `<project>-analytics/`
  bundle to a location outside version control (e.g. a gitignored tmp dir),
  matching the same discipline `pack` already enforces for real projects.
- **Data**: sibling plugins (`investing-toolkit/tests/`) establish the
  repo's pytest convention (`conftest.py`, `test_*.py`) — the deterministic
  half of this harness (fixture loader, gold-question grader, DuckDB query
  comparison) should follow that convention rather than inventing a new
  one.
- **Boundary**: no CI workflow currently runs any plugin's Python tests
  against a live Claude invocation — this is the first harness in the repo
  that calls `claude -p` as part of its own test surface. Scope of W1 is
  building + one manual validation run; wiring it into automated CI/nightly
  is explicitly Phase 4 (U1/U2), out of scope here.

Evidence paths: `dbt-wiki/skills/init/SKILL.md`, `dbt-wiki/skills/pack/SKILL.md`,
`dbt-wiki/.claude-plugin/plugin.json`, `investing-toolkit/tests/`.

## Decision

Build, in `dbt-wiki/tests/fixtures/`: a synthetic dbt-duckdb project with the
5 named traps + seeded data; `gold-questions.yml`; a deterministic grader +
fixture-loading layer under pytest (TDD, matching repo convention); and a
runner script that shells out to `claude -p` to drive
`/dbt-wiki:init` → `/dbt-wiki:pack` → blind Q&A against the fixture, capturing
answers for the grader to score. Execute one real end-to-end run this session
to prove the harness works end-to-end, using subscription quota. Do NOT wire
this into CI or a nightly loop — that's Phase 4.

## Out of Scope

- Additional fixture matrix cells (en-language project, sparse-comment
  project, non-duckdb dialects, 100+ model scale) — Phase 3 (G1).
- Gold-question difficulty ladder beyond the initial trap set — Phase 3 (G3).
- Automated nightly/CI wiring, budget breakers, kill-switch — Phase 4 (U1/U2).
- Cross-doc consistency lint (W2) — separate work item.
- Fixing any Phase 2 backlog defects the harness might surface — those get
  filed as new backlog items, not fixed inline during W1.

## What Becomes Obsolete

(Axis 5) Manual private-repo dogfooding as the *primary* validation signal
for "did this change help SQL-answering accuracy" is superseded — future
campaign decisions should cite the harness's grader output, not a private
dogfood round, as the evidence for "effective SQL skill" claims. Nothing to
delete in-repo (dogfooding was never checked-in code), but the Journal
should stop treating dogfood convergence as sufficient evidence once W1
ships.

## Alternatives Considered

Runner mechanism (Axis 4, WebSearch-grounded):
1. **`claude -p` headless CLI** — officially documented non-interactive mode
   for CI/scripted use (JA source: Qiita "Claude Code -p（ヘッドレス）実践パターン集
   — CI自動化"; EN: harness-engineering surveys describe headless API mode for
   CI/CD agent runs). Drives the exact same skill-invocation path a real user
   gets. **Chosen** — matches what the campaign doc already assumed, and
   uses subscription quota per user's clarification (not separate metered
   API cost).
2. **Claude Agent SDK (Python/TS)** — programmatic control, easier
   structured-output capture. Rejected: adds a second, subtly different
   agent-loop implementation to validate alongside the CLI users actually
   get; redundant with what `-p` already provides for this use case.
3. **Deterministic simulation (no real LLM)** — fast, free, fully
   repeatable. Rejected as the *only* mechanism: it would validate the
   fixture/grader plumbing but never test whether a blind agent, given only
   the packed skill, actually produces correct SQL — the exact claim W1
   exists to measure. Kept as the fast/deterministic half (fixture + grader
   unit tests), paired with #1 for the real e2e proof.

## Open Questions

- Exact invariant-checking mechanism for `gold-questions.yml` (regex/AST
  anti-pattern check vs. a second LLM-as-judge pass) is not yet decided —
  defer to planning stage; likely mechanical (grep/sqlglot AST check for
  "used the trap column directly" etc.) to keep grading deterministic and
  cheap, consistent with alternative #3 being the fast half.
