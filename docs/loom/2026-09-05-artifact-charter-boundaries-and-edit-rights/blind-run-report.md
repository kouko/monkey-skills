## 你要的東西，逐條試

### 1. 我可以在 loom-code 的 contract 裡打開一張表，每種 loom 文件一列，每列都有「該寫什麼、不該寫什麼（及其該去哪）、定稿點、定稿後允許的變動」四欄，沒有空格；「不該寫什麼」那欄每一條都指向另一份文件。
- **怎麼試的**：在乾淨副本裡直接叫出憲章表這個指令。
- **發生了什麼**：印出八列（intent、spec、plan、review、blind-run-report、memory、kickoff-defaults、dispatch），每列六欄（回答什麼／給誰讀／該寫什麼／不該寫什麼→去哪／定稿點／定稿後允許的變動）全部有內容，沒有一格空白；「不該寫什麼」每一條都寫著要去哪一份文件（例如 plan 的「設計理由 → spec」「往事日誌 → review」）。
- **證據**：指令輸出（八列 × 六欄，逐格檢查過）。
- **判定**：可以 — 表存在且沒有空欄。

### 2. 我把那個 dbt 專案 3,945 字的 plan.md 拿給 checker，它會指出 Risks 段裡的事後日誌與 `landed:` task 是 confirmed 後不允許的變動，並說明每一條該搬去哪份文件。
- **怎麼試的**：真正的那份 dbt 專案不在這個 repo 裡，我不能真的把它餵給 checker；改用一份「代打」的小 plan——先照模板 commit 一次（相當於定稿），再模仿那份 3,945 字 plan 的兩個毛病，各自補一刀：在 Risks 段追加一條帶日期的「LESSON」日誌，並在 Task 段追加一個帶 `landed: <sha>` 標記的新任務。這是代打樣本，不是真的那份 dbt plan。
- **發生了什麼**：checker 擋下兩條，各自點名去處：
  - `BLOCK plan.edits-after-commit: T2 added; goes to dispatch`
  - `BLOCK plan.edits-after-commit: Risks section changed; goes to review`
- **證據**：上面兩行指令輸出，逐字。
- **判定**：可以（在代打樣本上）— 兩種毛病都被擋下且各自點名去處；沒有拿到真正那份 3,945 字的 plan 直接驗證。

### 3. 我把一份三欄都在帽內的 plan.md 拿給 checker，它通過；把 Test 欄擴寫成情境清單後再給它，它擋下並指出超帽的欄位。
- **怎麼試的**：直接拿這次變更自己的 plan.md（三欄都在帽內）跑一次；再複製一份，把其中一個 Test 欄改寫成逐條情境清單（65 字），再跑一次。

- **證據**：兩次指令輸出。
- **判定**：可以。

### 4. 我拿一份舊的長 plan（kumiko 或該 dbt 專案）依憲章縮寫，冷派一個 implementer 給縮寫版與原版各一次，縮寫版回 NEEDS_CONTEXT 的次數不多於原版；報告附兩次派工的狀態回報。
- **怎麼試的**：讀了已存的 A/B 對照證據——同一個任務（kumiko 專案的木色預設值更正）分別用原版 plan（4,633 字）與憲章版 plan（941 字）各冷派兩次 implementer，共四次派工，狀態回報逐字存檔。
- **發生了什麼**：兩組結果都是「憲章版問得比原版多」：
  | 派工 | 用哪份 plan | 狀態 | 需要追問的次數 |
  |---|---|---|---|
  | A1 | 原版（4,633 字） | DONE | 2 |
  | B1 | 憲章版（941 字） | NEEDS_CONTEXT | 3 |
  | A2 | 原版 | DONE_WITH_CONCERNS | 2 |
  | B2 | 憲章版 | DONE_WITH_CONCERNS | 4 |

  驗收條件寫的是「憲章版的追問次數不超過原版」，這次樣本上**沒有達成**（3 比 2、4 比 2，憲章版都比原版多問）。我如實照登，不幫忙緩頰。

  多問出來的那一條，兩組都一樣：憲章版特有的追問是「設計理由」——為什麼用某個品名而不是另一個說法的緣由。憲章規定這種設計理由要住在 spec 裡，但這次連同這份「文件憲章」本身在內的工程性變更都沒有 spec，理由就沒地方住,implementer 只好開口問。第二組（B2）還多問了兩條，是憲章版的 Test 欄裡帶著一句從原版整段話裡摘出來、卻少了上下文而顯得矛盾的殘句。

  沒被數字說出來的另一面：憲章版短了八成，而且每一條多問出來的問題，答案都只要一行話就能講完——原版之所以問得少，是因為它把設計理由整段寫進了 plan 裡。要縮短的話，代價是這些理由现在要有一個地方放；這正是本變更遺留的一個問題（見「我幫你決定的事」）。
- **證據**：四份逐字狀態回報檔（A1/A2 原版、B1/B2 憲章版）與一份彙整說明。
- **判定**：部分達成，且明確沒過驗收條件的字面比較 — 憲章版問得比原版多，原因記在案。

### 5. 我用一份含「plan 少列一個測試情境」的假 finding 冷派 reviewer，它依收窄後的 omission 定義不把這條當 omission；用一份 plan 內含 REQ 重述的樣本冷派，它標 inconsistency 並指向憲章。
- **怎麼試的**：造了兩份小樣本——(甲) 一份沒有列情境清單的 plan，外加一條「說 plan 沒把三種輸入情境分開列」的候選意見；(乙) 一份 Test 欄整句重述一條 REQ 編號和選擇理由的 plan。用 `codex exec --sandbox read-only` 開一個全新、沒有記憶的讀者,只給它憲章相關文件和這兩份樣本去判。
- **發生了什麼**：冷讀者的判定——
  - 甲：**不算 omission**，引用「REQ 沒重述、情境沒列出、理由沒寫，都算完整」這條收窄後的定義。
  - 乙：**算 inconsistency**，引用「符合『不該寫』那一欄內容的東西出現在 plan 裡就判 inconsistency」。
- **證據**：Codex 冷讀輸出，逐字引用兩條判定與其出處。
- **判定**：可以。

### 7. 整包測試通過，write-plan SKILL.md 仍在 4,500 字帽內。
- **怎麼試的**：跑了兩次完整測試指令；用 Python 的 `len(open(f).read().split())` 數 write-plan 的 SKILL.md 字數。

- **判定**：可以（帶一個已知的、非本次改動造成的偶發測試現象，見下方事實）。
