### 1. 打開一張憲章表，每種文件一列，四欄都不空，「不該寫什麼」指向另一份文件
- **怎麼試的**：在乾淨副本執行查表指令。
- **發生了什麼**：印出八種文件（intent、spec、plan、review、blind-run-report、memory、kickoff-defaults、dispatch）各一列，四欄都有內容；抽查「不該寫什麼」欄，每一條都寫著該搬去哪一份文件（例如 plan 的「行為或需求重述 → spec」）。
- **證據**：指令輸出 8 行完整表格，逐列人工核對無空格。
- **驗證**：可行。

### 2. 把一份 3,945 字的長 plan 拿給檢查工具，它指出哪些段落是定稿後不該有的變動，並說明該搬去哪
- **怎麼試的**：那份 dbt 專案的 plan 不在這個 repo 裡，我做了一個**替代樣本**：先提交一份乾淨的 plan（等同「定稿」），再追加一段帶日期的「LESSON」事後日誌與一個帶 `landed:` 標記的新任務，然後對這兩次提交跑檢查工具。
- **發生了什麼**：只加「LESSON」日誌時，工具擋下並說「Risks 段落被改，該去 review」；只加帶 `landed:` 的新任務時，工具擋下並說「該去 dispatch」。兩種都清楚點名該搬去哪份文件，但每次只指出第一個踩到的問題，不是一次列完全部。
- **證據**：兩次獨立試驗的指令輸出，各一行 BLOCK 訊息，分別指向 review 與 dispatch。
- **驗證**：可行，但是替代樣本，不是原題目那份 3,945 字的 plan。

### 3. 三欄都在字數帽內的 plan 通過；把 Test 欄擴寫成情境清單後被擋，並指出哪一欄超帽
- **怎麼試的**：寫一份 Test 欄在帽內的 plan 跑檢查；再把同一欄改成 41 個情境詞後重跑。
- **發生了什麼**：帽內版本通過（結束碼 0）；擴寫版本被擋，訊息明確點名是哪個任務、哪一欄、目前字數與帽（「T1.Test 41 words, cap 40」）。
- **證據**：兩次指令輸出。
- **驗證**：可行。

### 4. 拿一份舊的長 plan 依憲章縮寫，冷派一個 implementer 給縮寫版與原版各一次，比較卡關次數

- **證據**：目錄查詢顯示相關證據檔案不存在。
- **驗證**：尚未建置——這條驗收要等第 3 波做完才能試。

### 5. 用「plan 少列一個測試情境」的假 finding 冷派 reviewer，它不當成 omission；用含 REQ 重述的 plan 冷派，它標成 inconsistency 並指向憲章
- **怎麼試的**：準備兩份假 plan（都只給 reviewer 契約檔、審查用語定義檔、契約清單檔、那份 plan 這四個檔案，沒給別的），用一個全新啟動、沒看過這次對話的 Codex 冷讀，分別問兩個問題。
- **發生了什麼**：第一份 plan（Test 欄只寫一句、沒有列情境清單）配上假 finding「plan 少列一個測試情境是 omission」，冷讀的回答是**不算 omission**，逐字："Verdict: not omission. lenses.md states that, for a plan, 'a scenario left unlisted … is complete,' because manifest.yaml explicitly places 'scenario lists inside Test' in the plan charter's must_not column and sends them to the spec; W1-01 already has the required Test line."　第二份 plan 的 Test 欄寫成「REQ-2: the CLI prints the due date next to each task」，冷讀的回答是**標成 inconsistency**，並引用憲章的 must_not／goes_to，逐字（原文為日文）："inconsistency（不整合）… manifest.yaml の artifacts.plan.charter.must_not は『behaviour or REQ restatement』→ spec としています。W2-01 の Test 行は REQ-2 の振る舞いを再記述しているため、この行に該当します。"
- **證據**：兩次獨立 Codex 冷讀（`codex exec --sandbox read-only`）的完整回覆逐字保留。
- **驗證**：可行，兩個方向都如預期。

### 6. review.json 追加第二輪時，只有憲章允許追加的節點能長；對只能替換的節點追加第二份會被擋
- **怎麼試的**：做了一個**替代樣本**：先提交一份帶憲章版本戳記的 review.json（第一輪一則判定），再提交第二次只做「追加一則探針、替換 reviewed_sha」的合法變動並跑檢查；接著再提交第三次去改寫第一輪已存在的判定內容，重跑檢查。

- **證據**：三次獨立指令的輸出，合法通過、非法擋下各一行。
- **驗證**：可行，但是替代樣本，不是這次變更自己的 review.json（那份本身仍在持續累積中，不能拿來自證）。
