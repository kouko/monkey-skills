### 2. 我把那個 dbt 專案 3,945 字的 plan.md 拿給 checker，它會指出 Risks 段裡的事後日誌與 `landed:` task 是 confirmed 後不允許的變動，並說明每一條該搬去哪份文件。

### 4. 我拿一份舊的長 plan（kumiko 或該 dbt 專案）依憲章縮寫，冷派一個 implementer 給縮寫版與原版各一次，縮寫版回 NEEDS_CONTEXT 的次數不多於原版；報告附兩次派工的狀態回報。
- **怎麼試的**：讀了已存的 A/B 對照證據——同一個任務（kumiko 專案的木色預設值更正）分別用原版 plan（4,633 字）與憲章版 plan（941 字）各冷派兩次 implementer，共四次派工，狀態回報逐字存檔；我自己逐份重新數了每份回報裡「需要追問的次數」那一行，沒有照抄彙整表。修正輪之後,又追加了兩次派工:原版單獨一份、憲章版配上一份新增的 395 字「工程理由書」，同樣逐份重數。
- **發生了什麼**：前兩組（沒有工程理由書時）確實是「憲章版問得比原版多」，修正輪之後又補了兩組（憲章版配上工程理由書），結果反過來：
  | 派工 | 用哪份 plan | 狀態 | 需要追問的次數（我逐份重數） |
  |---|---|---|---|
  | A1 | 原版（4,633 字） | DONE | 2 |
  | B1 | 憲章版（941 字，無理由書） | NEEDS_CONTEXT | 3 |
  | A2 | 原版 | DONE_WITH_CONCERNS | 2 |
  | B2 | 憲章版（無理由書） | DONE_WITH_CONCERNS | 4 |
  | A3 | 原版 | DONE | 1 |
  | B3 | 憲章版 + 395 字工程理由書 | DONE_WITH_CONCERNS | 0 |
  | A4 | 原版 | DONE | 3 |
  | B4 | 憲章版 + 工程理由書 | DONE_WITH_CONCERNS | 1 |

  驗收條件寫的是「憲章版的追問次數不超過原版」。前兩組（B1、B2）**沒有達成**（3 比 2、4 比 2，憲章版問得比原版多）；修正輪補上「工程理由書」這個新地方之後,後兩組（B3、B4）**達成了**（0 比 1、1 比 3，憲章版反而問得比原版少）。兩種結果我都照登，不用後面的結果蓋掉前面的。

  前兩組多問出來的那一條，兩組都一樣：憲章版特有的追問是「設計理由」——為什麼用某個品名而不是另一個說法的緣由。憲章規定這種設計理由要住在 spec 裡，但這次連同這份「文件憲章」本身在內的工程性變更原本沒有 spec，理由就沒地方住,implementer 只好開口問。第二組（B2）還多問了兩條，是憲章版的 Test 欄裡帶著一句從原版整段話裡摘出來、卻少了上下文而顯得矛盾的殘句。

  修正輪做的事，正是把這個沒地方住的問題補上：現在工程性變更也能有一份 395 字的「理由書」（跟 spec 走同一套機制，但不用像產品變更那樣多開一個人類確認關卡）。補上理由書之後,B3 完全不用開口問（原版倒是自己問了一題）,B4 只問一句無關設計理由的格式小問題，比原版少問兩句。前兩組沒過的原因就是這份理由書修正輪之前還不存在。
- **證據**：八份逐字狀態回報檔（A1–A4 原版、B1–B4 憲章版，含配理由書的兩份），每份的追問次數都是我自己重新點過的，不是抄彙整表。
- **判定**：部分達成，兩段都要看——原本的樣本（B1、B2）沒過，修正輪補上工程理由書之後新跑的樣本（B3、B4）過了；兩段都如實記錄，不互相取代。

### 5. 我用一份含「plan 少列一個測試情境」的假 finding 冷派 reviewer，它依收窄後的 omission 定義不把這條當 omission；用一份 plan 內含 REQ 重述的樣本冷派，它標 inconsistency 並指向憲章。
