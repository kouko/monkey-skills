# Spec red-team — 2026-09-03-loom-post-merge-seams (round 1)

1. **PR spoofing / never-merged / unmerged PR / bogus PR#N.** escapes — REQ-1's design only requires the status line match the *grammar* `closed <date> — PR #<N>`; nothing recomputes that PR #N exists or merged (contrast principle #3: "no gate trusts a claim written by the agent it checks"). An agent can push `status: closed 2026-09-03 — PR #999999` (nonexistent) or the number of an open, unmerged PR and the push gate (a docs-only, one-line diff) sails through untouched — no code paths trigger `push.probes-adversarial`/review linkage. Fix: add a rule (or extend `push.review-only-head`'s new branch) that resolves PR #N via `gh` against the merge-base and requires it MERGED, or at minimum requires the intent's prior status to have been `confirmed` with a review.json PASS on file before accepting `closed`. **fatal.**

2. **Future/garbage date on `closed`.** escapes — `confirmed` reuses `is_real_date()`; the design decision for `closed` never says it does. `closed 2099-12-31 — PR #1` is grammar-valid but never checked for realism, unlike its sibling state. Fix: state explicitly that the closed-date branch also calls `is_real_date`. **important** (decision-map reads this for delivery state, per REQ-5's stated consumer).

3. **Rename-based smuggling.** escapes — `check_review_only_head` explicitly disables rename detection (`--no-renames`) with a comment naming exactly this attack (collapsing a delete+add into one path). REQ-1's design decision for the new "closed" shape never states the same `--no-renames` requirement; a renamed-with-modification intent file could present as "one file, one line" under git's similarity heuristics while smuggling extra edits. Fix: one sentence pinning `--no-renames` for the new branch, same as the sibling check. **important.**

4. **Second file in the same commit (another intent, or an unrelated file).** holds — design decision states explicitly: "a closing commit that also edits another file is still blocked" and REQ-1 requires HEAD to touch "exactly one file under docs/loom/intent/".

5. **Second hunk in the same file / whitespace-only extra edit / CRLF noise elsewhere in the file.** holds — "the diff of that file is exactly one line — the status: line" forbids any other changed line, whitespace or not.

6. **Silent re-open of a `closed` intent (hand-edit back to `confirmed <date>`) then re-plan.** escapes — the design decision only describes `intake.confirmed` blocking *while* status reads `closed`; nothing makes `closed` a one-way/terminal state the checker enforces (no rule rejects a commit that changes status from `closed` back to `confirmed`, and REQ-1's new push-gate branch only fires forward, closed→nothing-else is unconstrained). REQ-2's own open question ("can a closed intent be re-opened silently... should that be blocked") is answered nowhere in the spec text. Fix: add a rule (or extend `intake.confirmed`) that rejects reverting `closed` → `confirmed` outside the one recognized transition, or require the reopen to go through a fresh `capture-intent`. **important.**

7. **Hiding real gate-relevant work under `.codex/hooks/contract/`.** escapes — REQ-3 wires `check_dispatch_covers_tasks` through the *same* `_is_host_plumbing` predicate `changed_paths` already uses, and that predicate is a **path-prefix match**, not a content check against what `codex_scaffold.py`'s `CONTRACT_COPY` actually generates. Dropping any file (hand-authored or altered) under `.codex/hooks/contract/` was already invisible to `push.probes-adversarial`/`changed_paths`; REQ-3 now *also* exempts it from `Task:` trailer duty, doubling the surface with zero new verification that the bytes match scaffold output. The spec's own comment block (loom_checker.py:380-388) names the boundary as "exactly what the Codex scaffold writes" but the code enforces only the directory prefix. Fix: hash-check the copy against a fresh scaffold run, or accept the pre-existing risk explicitly and say so as a stated limitation rather than silently widening it. **fatal.**

8. **REQ-4/5/6 falsifiability.** REQ-4's "one line of recommendation" and the table are checkable by inspection (file exists, has the table, cites #771's 34/31) — falsifiable. REQ-5 is checkable (`--list-rules` version string). REQ-6 nits are each pinned to a `file:line` and a specific assertion — falsifiable. No escapes found here.

Verdict: **NEEDS_REVISION** — escapes: 3 fatal (#1, #7, plus #1's blast radius makes the whole close-commit exemption a way to *claim* ship without proof), 3 important (#2, #3, #6), 0 nit.
