## Requirements
REQ-1 — Intent closed on the branch before the merge, under the unchanged push gate
  The ship station's order becomes: push → `gh pr create` (the PR number is now known) → commit `docs(loom): close intent <change-id>` changing that intent's `status:` line from `confirmed <date>` to `closed <YYYY-MM-DD> — PR #<N>` → the review station runs one more round over `<reviewed_sha>..<close commit>`, as it does for any commit made after the branch-end pass: scope `branch-end`, the delta is `intent`-typed so two fresh-context reviewers read it under the docs + user-judgment-leak lenses and each must state that the delta is that one status line and nothing else, every verdict of the round records `sha: <close commit>`, package-tests and adversarial probes are re-pinned at the close commit (the checker re-runs both itself at push), and no blind run is owed for an intent-typed delta → its review-only commit (only `review.json`; `reviewed_sha` = the close commit) → push again. `loom_checker.py push` passes on its existing rules, no rule gains a shape and nothing is bypassed; the user reads no diff at any point; `closed` reaches the trunk only by the merge. `loom_checker.py intake write-plan <change-id>` on a closed intent blocks with `intake.confirmed: … this change is closed (PR #<N>); a new change starts from a new intent`. The already-merged intent `2026-09-02-simple-loom-flow` is closed the same way inside this change's own diff. Two residuals are stated, not hidden: the checker ties probes to `reviewed_sha` (`push.probes-package-tests`, `push.probes-adversarial`) but not the latest round's verdicts, so an agent that skips the close-commit round and moves `reviewed_sha` by hand is stopped by the ship station's text, not by a rule — a gap that exists today for every commit made after a branch-end pass, is not widened by this change, and goes to a follow-up intent (tying `verdicts[].sha` to `reviewed_sha` changes a rule's semantics, which the Constraint excludes); and CI does not run `loom_checker.py push` (the push gate is client-side; CI recomputes the intake/standing/contract rules, the mechanism population and the package tests) → Acceptance #1
REQ-2 — Contract grammar knows `closed`, and closed is terminal
  `loom-code/contract/manifest.yaml` (`status` grammar) and `loom-code/contract/templates/intent.md` (status comment) both list `closed <YYYY-MM-DD> — PR #<N>`; the date must pass the same `is_real_date()` the `confirmed` branch uses (a real calendar date; the checker does not compare it to today's clock) and `<N>` is a positive integer; `--list-rules` describes it under `intake.confirmed`; **terminal**: `intake.confirmed` also blocks, with the message `intake.confirmed: <change-id> was closed (PR #<N>) and closed intents are not reopened; start a new intent`, when either (i) the intent file's history on the current branch shows a `closed` status while the current status is anything else — `git log --format=%H -G<pattern> -- <intent path>` non-empty, where `<pattern>` is rendered from the status regex's own `closed` alternative (same whitespace tolerance), so the history search and the grammar cannot disagree on a hand-edited line — or (ii) the trunk's copy of the file parses as `closed` (`git show <trunk>:<intent path>`, `<trunk>` being the first of `TRUNK_CANDIDATES` that resolves; skipped when none does). A reopen therefore cannot enter write-plan or write-spec on a branch that carries the close commit, nor on a branch cut from the trunk before the merge once the local trunk ref carries the merge; the boundary is stated exactly: case (i) holds while the commit that introduced `closed` is in the branch's ancestry (deleting and re-adding the path does not remove it from `git log -- <path>`; only rewritten ancestry does), and case (ii) is as current as the last fetch of the trunk ref — no network is touched, and a never-fetched trunk ref is the stated residual; `test_the_repos_own_change_matches_its_own_review_json` derives `{intake.confirmed}` as the expected block when the repo's own intent is closed; the declared package command `python3 -m pytest loom-code/scripts/ scripts/ .claude/hooks/ -q` passes locally, and the CI job `pytest + knowledge-drift + codex-manifest-drift` (.github/workflows/loom-code-ci.yml:114, same paths with `-v`; only the exit code must agree) passes → Acceptance #2
REQ-3 — Scaffold copy is host plumbing for the trailer rule too, by content, where a canonical exists

A commit that only refreshes `.codex/hooks/` with genuine scaffold output then carries no trailer duty; an altered, added, deleted or mode-changed entry under those paths counts as gate work and needs a trailer. When the checker doing the push is the copy (Codex in an adopting repo) there is no canonical to compare against and no exemption applies — every plumbing edit keeps trailer duty, exactly as today → Acceptance #3

## Design decision
- **Close before the merge (user-decided 2026-09-03; replaces round 1's new push shape).** The intent is closed on the change branch once the PR number exists; the close commit is then reviewed by the review station like any other commit made after the branch-end pass — two fresh reviewers on the one-line delta, probes re-pinned — and only then does the review-only commit move `reviewed_sha` to it. Nobody reads the diff for quality: not the user (PRINCIPLES.md Non-negotiables 1–2, spec-C9 of round 3), and not the agent that wrote it. Cost: one extra read-only round per shipped change (two reviewers on a one-line intent delta, no blind run); REQ-4's table counts it. Consequences: no push rule changes (the intent Constraint stands as written); the closed line lands on the trunk with the squash and nowhere else, so a `closed` on the trunk is itself the proof of the merge — no PR-number verification is needed and none is done; a PR that is never merged leaves `closed` on a dead branch only. The ship station text (`loom-code/skills/ship/SKILL.md` §6) is rewritten to this order, and its "the status line cannot be written on the branch" paragraph goes. Rejected: the round-1 design (a second accepted HEAD shape for `push.review-only-head`) — one more rule semantics, a grammar-only proof, and every red-team escape listed in evidence/spec-redteam-r1.md.
- **`intake.confirmed` on a closed intent (agent-decided).** Blocks with the message above; `closed` is not a pass state anywhere. The status grammar is one regex in `loom_checker.py` shared by `intake.confirmed` and `intent.schema`, so the two cannot drift; the closed date goes through `is_real_date()` in the same branch as `confirmed`. The reopen check recomputes twice (REQ-2): the branch's own history through a `-G` pattern rendered from the same regex, and the trunk ref's copy of the file; neither is a flag an agent writes, and the pattern cannot drift from the grammar because it is derived from it.
- **Content-bound plumbing exemption, only with an external canonical (agent-decided; round 2 spec-C6/R7).** `check_dispatch_covers_tasks` filters `commit_paths()` through `_is_host_plumbing()` (loom_checker.py:400) **and** a blob comparison against a canonical the running checker can name without trusting the repo: the checker doing the push is the file the host hook invokes — Claude Code's `hooks.json` in the loaded plugin cache, Codex's `.codex/hooks/loom-checker` (untouched, per the Constraint) — and it identifies itself by `Path(__file__).resolve()` **plus** a contract package beside it (`../contract/manifest.yaml` relative to its own directory): a checker under the repo's `.codex/hooks/`, or one with no contract package beside it (a stray copy or symlink anywhere else), has no canonical and the exemption is off (the Codex case; the artifact-content gap of concept-model §7 is not widened by this change). What an agent runs by hand is not the gate — only the hook-invoked checker's verdict is — so a copy or symlink placed elsewhere buys nothing on Codex (red team 2e), and an older cached plugin version run by hand is not the hook's canonical (2f). Otherwise the canonical is the source tree the checker runs from: `.codex/hooks/loom_checker.py` and `git_exec.py` must equal `<that dir>/loom_checker.py` / `git_exec.py` with the copy's stamp line (`# loom-checker <version>`) stripped — after the stamp's version has been compared with the running checker's own version, so a copy that matches a superseded release fails before any blob is read; `.codex/hooks/loom-checker` must equal the shim `codex_scaffold.SHIM_TEMPLATE` renders for that version; `.codex/hooks/contract/<rel>` must equal `<that dir>/../contract/<rel>`; `.loom-hook-fired` is ignored. "Two cached plugin versions" is not ambiguous: the canonical is whichever checkout the hook invoked (the hooks.json of the version Claude Code loaded), and a copy stamped with another version simply fails the comparison and owes a trailer. A plumbing path with no canonical counterpart (an extra file under `contract/`) fails the comparison. Recorded limitation: on Codex the scaffold refresh commit (and the first-contact scaffold commit of `write-plan` step 0b) still needs a `Task:` trailer, which is a seam of its own — it goes to a follow-up intent, not this change.
- **Test oracle for the self-check (agent-decided).** `test_the_repos_own_change_matches_its_own_review_json` (loom-code/scripts/test_loom_checker_intake.py:385-447) derives its expected block set dynamically; it gains the branch: intent status `closed …` → expected `{intake.confirmed}`. The CI failure it currently produces is kept as `evidence/ci-781-intake-confirmed.md`.
- **Contract version (agent-decided).** Stays 1.0: an added accepted value is backward compatible for every consumer requiring `>=1.0`. Plugin bumps as REQ-5.
- **Checkpoint-cost table (agent-decided).** Written by the blind-runner at branch end from `git log` and `review.json`, so the numbers are recomputed by someone who did not produce them. Recommendation only — the decision is deferred to the second and third real change (user-decided 2026-09-03).
- **Merge (user-decided 2026-09-03).** The user presses merge; the agent stops after `gh pr create`.
- **Test nits (agent-decided).** Fixed in the task that already touches each file (`test_check_mechanisms.py`: R28-O2, R30-O1, R30-O2; `test_session_start_words.py`: R30-O3; `loom_checker.py`: R24-O2); R30-O2's guard asserts, via `inspect.getsource(check_mechanisms)`, that no `subprocess` call in the module names `wc`.

## Alternatives considered
- A `push` flag or waiver for docs-only commits — rejected: a declared bypass; the design has no waivers.
- A second accepted HEAD shape for `push.review-only-head` with the merge proven from the parent tree (round-1 design) — rejected: one more rule semantics and a grammar-only PR pointer; superseded by closing on the branch.
- A checker rule asserting the close commit's diff shape (round-3 fix proposal) — rejected: a 28th rule against the Constraint and PRINCIPLES.md principle 4's budget; the review station already reads every post-pass commit with two fresh reviewers, and the only untied part (verdict sha) is a pre-existing gap recorded for a follow-up intent.
- Writing `closed` inside the review-only commit itself — rejected: that commit may touch only review.json; the close is its own commit immediately before it.
- Exempting plumbing paths by prefix for the trailer rule (round-1 design) — rejected by the red team: it lets gate content hide under `.codex/hooks/contract/`.
- Bumping only loom-code — rejected: Acceptance #5 (user-confirmed) and both sibling plugins describe the status values in prose.
