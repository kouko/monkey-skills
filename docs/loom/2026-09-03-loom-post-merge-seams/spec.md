## Requirements
REQ-1 — Intent closed on the branch before the merge, under the unchanged push gate
  The ship station's order becomes: push → `gh pr create` (the PR number is now known) → commit `docs(loom): close intent <change-id>` changing that intent's `status:` line from `confirmed <date>` to `closed <YYYY-MM-DD> — PR #<N>` → the ship station invokes `loom-code:review` again with scope `branch-end` over `<reviewed_sha>..<close commit>`, as it does for any commit made after the branch-end pass: the delta is `intent`-typed so two fresh-context reviewers read it under the docs + user-judgment-leak lenses and each must state that the delta is that one status line and nothing else, every verdict of the round records `sha: <close commit>`, package-tests and adversarial probes are re-pinned at the close commit (the checker re-runs both itself at push), and no blind run is owed because the delta is intent-typed (the artifact-type table: a one-line status change has no Acceptance content to walk; the branch-end blind-run report already covers the change) → its review-only commit (only `review.json`; `reviewed_sha` = the close commit) → push again. `loom_checker.py push` passes on its existing rule ids — no new rule, no waiver — and two of them are **tightened** (user-decided 2026-09-03, option A): `push.reviewed-sha` also requires **every** verdict of the latest round — the same round `scored_verdicts()` hands `check_verdicts` — to carry `sha`, and every such `sha` must resolve to the same object as `reviewed_sha` (compared as git object ids, like `reviewed_sha` itself). There is no exemption by `scope`: a scope label is a claim, not a recompute (round 6 spec-R21), so a mixed round with one untied verdict fails, and a spec-only round — which records `spec_sha` for `intake.spec-pass` and vouches for a blob, not a commit — is simply never a round a push can ride on. A round that reviewed an older delta therefore cannot vouch for a newer `reviewed_sha`; and `push.review-only-head` also recomputes the reviewed commit's shape when it introduces a `closed` status: if `git show --raw --no-renames HEAD^` touches an intent file whose `status:` line changes to `closed …`, that commit must touch exactly that one file, its diff against its parent (`git diff -U0 HEAD^^ HEAD^ -- <that path>`) must consist of exactly one removed and one added line, both `status:` lines, the added one matching the `closed` alternative of the shared status regex — **and** its parent `HEAD^^` must itself be a checkpoint, i.e. a commit that touches only `review.json` and whose `review.json` records a `reviewed_sha` resolving to `HEAD^^^` (the two shapes this rule and `push.reviewed-sha` already demand of `HEAD`), so no commit can sit between the last checkpoint and the close commit without a checkpoint of its own (round 6 spec-R22: a docs-typed commit interposed there would otherwise be invisible to every push rule). A checkpoint fabricated for an interposed commit needs forged verdicts, which the checker's own stated boundary excludes (loom_checker.py §0: a forged record is out of scope) and which the dispatch records leave visible; a close commit or parent of any other shape is refused. Both are recomputes from the repository; each failure message names the rule id, the offending commit or field and the value expected, in the implementer's words like every existing rule, and the checker collects every failure rather than stopping at the first, so both rules report when both faults are present. The user reads no diff at any point; under the stated assumption that the trunk receives only merges (Design decision 1), `closed` reaches the trunk only by the merge. `loom_checker.py intake write-plan <change-id>` on a closed intent blocks with `intake.confirmed: … this change is closed (PR #<N>); a new change starts from a new intent`. The already-merged intent `2026-09-02-simple-loom-flow` is closed the same way inside this change's own diff. Closed by the tightening (round 5 spec-C11, formerly stated as residuals): an agent that skips the close-commit round and moves `reviewed_sha` by hand is now refused by `push.reviewed-sha` (the latest round's verdicts name an older commit), for every commit made after a branch-end pass and not only the close commit; and "the delta is that one status line" is recomputed by `push.review-only-head`, not taken from the reviewers. One residual is stated, not hidden: CI does not run `loom_checker.py push` (the push gate is client-side; CI recomputes the intake/standing/contract rules, the mechanism population and the package tests) → Acceptance #1
REQ-2 — Contract grammar knows `closed`, and closed is terminal
  `loom-code/contract/manifest.yaml` (`status` grammar) and `loom-code/contract/templates/intent.md` (status comment) both list `closed <YYYY-MM-DD> — PR #<N>`; the date must pass the same `is_real_date()` the `confirmed` branch uses (a real calendar date; the checker does not compare it to today's clock) and `<N>` is a positive integer; `--list-rules` describes it under `intake.confirmed`; the grammar is one regex, `STATUS`, replacing today's `CONFIRMED` (loom_checker.py:791): `open | confirmed <date> | closed <date> — PR #<N> | withdrawn — <reason>`, each alternative allowing the trailing `\s+#.*` comment `CONFIRMED` allows today, shared by `intent.schema`, `intake.confirmed` and `push.review-only-head`; **terminal**: `intake.confirmed` also blocks, with the message `intake.confirmed: <change-id> was closed (PR #<N>) and closed intents are not reopened; start a new intent`, when either (i) the intent file's history on the current branch shows a `closed` status while the current status is anything else — `git log --format=%H -G'^status:[[:space:]]*closed ' -- <intent path>` non-empty, the pattern being rendered from the `closed` alternative of `STATUS` with the same optional whitespace the frontmatter parser strips between `status:` and its value, so the history search and the grammar cannot disagree on a hand-edited line — or (ii) the trunk's copy of the file parses as `closed` (`git show <trunk>:<intent path>`, `<trunk>` being the first of `REOPEN_TRUNK_CANDIDATES = ("origin/main", "main", "origin/master", "master")` that resolves — a second, named constant, **not** `TRUNK_CANDIDATES`, whose trailing `@{upstream}` `branch_base` keeps but which may name the change branch's own remote copy; when none of the four resolves, case (ii) is absent, not stale, and the checker prints that it is absent). A reopen therefore cannot enter write-plan or write-spec on a branch that carries the close commit, nor on a branch cut from the trunk before the merge once the local trunk ref carries the merge; the boundary is stated exactly: case (i) holds while the commit that introduced `closed` is in the branch's ancestry (deleting and re-adding the path does not remove it from `git log -- <path>`; only rewritten ancestry does), and case (ii) is as current as the last fetch of the trunk ref — no network is touched. Three stated residuals: a stale trunk ref (fetched before the merge) gives partial protection; a ref of the right name that was never fetched at all — created locally (`git branch main <old sha>`, `git update-ref refs/remotes/origin/main …`) — is indistinguishable from a real one, because case (ii) trusts whatever local ref resolves under those four names and verifies no fetch provenance (single-user shaping their own gate, same class as the downgraded plugin); a clone with no trunk ref at all (shallow or single-branch, no `main`/`origin/main`) plus rewritten ancestry has neither check live, and a reopen there is caught only when the branch is pushed to a remote whose trunk carries the close — nothing in this change closes that; `test_the_repos_own_change_matches_its_own_review_json` derives `{intake.confirmed}` as the expected block when the repo's own intent is closed; the declared package command `python3 -m pytest loom-code/scripts/ scripts/ .claude/hooks/ -q` passes locally, and the CI job `pytest + knowledge-drift + codex-manifest-drift` (.github/workflows/loom-code-ci.yml:114, same paths with `-v`; only the exit code must agree) passes → Acceptance #2

## Design decision
- **Close before the merge (user-decided 2026-09-03; replaces round 1's new push shape).** The intent is closed on the change branch once the PR number exists; the close commit is then reviewed by the review station like any other commit made after the branch-end pass — two fresh reviewers on the one-line delta, probes re-pinned — and only then does the review-only commit move `reviewed_sha` to it. Nobody reads the diff for quality: not the user (PRINCIPLES.md Non-negotiables 1–2, spec-C9 of round 3), and not the agent that wrote it. Cost: one extra read-only round per shipped change (two reviewers on a one-line intent delta, no blind run); REQ-4's table counts it. Every existing test fixture that builds a `review.json` with verdicts gains `sha` in its helper — one helper, not per test — and this repo's own `review.json` carries `sha` on every verdict from the first build-phase round on. Consequences: two push rules are tightened, none added and none waived (the intent Constraint amended by kouko, option A, 2026-09-03); the verdict grammar gains `sha` — additive, contract stays 1.0 — and `verdicts[].sha` is required only on non-`spec` scopes because a spec round reviews a blob (`spec_sha`), not a commit; the closed line lands on the trunk with the squash and nowhere else, so a `closed` on the trunk is the proof of the merge **on the assumption that the trunk receives only merges** — loom does not verify the PR number and does not check who can push to the trunk; this repo's own branch protection leaves `enforce_admins` off with zero required approvals, so an admin pushing `closed` straight to `main` is not caught by anything here (stated assumption, not a property; out of scope with the other multi-user cheating cases); a PR that is never merged leaves `closed` on a dead branch only. The ship station text (`loom-code/skills/ship/SKILL.md` §6) is rewritten to this order, and its "the status line cannot be written on the branch" paragraph goes. Rejected: the round-1 design (a second accepted HEAD shape for `push.review-only-head`) — one more rule semantics, a grammar-only proof, and every red-team escape listed in evidence/spec-redteam-r1.md.
- **`intake.confirmed` on a closed intent (agent-decided).** Blocks with the message above; `closed` is not a pass state anywhere. The status grammar is one regex in `loom_checker.py` shared by `intake.confirmed` and `intent.schema`, so the two cannot drift; the closed date goes through `is_real_date()` in the same branch as `confirmed`. The reopen check recomputes twice (REQ-2): the branch's own history through a `-G` pattern rendered from the same regex, and the trunk ref's copy of the file; neither is a flag an agent writes, and the pattern cannot drift from the grammar because it is derived from it.
- **Content-bound plumbing exemption, only with an external canonical (agent-decided; round 2 spec-C6/R7).** `check_dispatch_covers_tasks` filters `commit_paths()` through `_is_host_plumbing()` (loom_checker.py:400) **and** a blob comparison against a canonical the running checker can name without trusting the repo: the checker doing the push is the file the host hook invokes — Claude Code's `hooks.json` in the loaded plugin cache, Codex's `.codex/hooks/loom-checker` (untouched, per the Constraint) — and it identifies itself by the path it was **invoked** as — `Path(__file__)` without `.resolve()`, i.e. the literal `{checker}` argument the Codex shim passes (`codex_scaffold.SHIM_TEMPLATE`) or the plugin-cache path in `hooks.json` — never the symlink-resolved real path, because a symlinked `.codex/hooks/loom_checker.py` pointing at a genuine canonical would otherwise resolve outside `.codex/hooks/` and classify itself as canonical (round 5 spec-R20); **plus** a contract package in the place its own layout puts it — `../contract/manifest.yaml` for a plugin checkout or this repo (`scripts/` beside `contract/`), while the Codex scaffold writes `contract/` inside `.codex/hooks/` itself (`codex_scaffold.CONTRACT_COPY`, the source of truth for that layout). The order of the test matters: a checker whose invoked path lies under the repo's `.codex/hooks/` is the copy and is excluded first; only then is the sibling contract package looked for, and one with none (a stray copy or symlink anywhere else) has no canonical. In both cases the exemption is off (the Codex case; the artifact-content gap of concept-model §7 is not widened by this change). What an agent runs by hand is not the gate — only the hook-invoked checker's verdict is — so a copy or symlink placed elsewhere buys nothing on Codex (red team 2e), and an older cached plugin version run by hand is not the hook's canonical (2f). Otherwise the canonical is the source tree the checker runs from: `.codex/hooks/loom_checker.py` and `git_exec.py` must equal `<that dir>/loom_checker.py` / `git_exec.py` with the copy's stamp line (`# loom-checker <version>`) stripped — after the stamp's version has been compared with the running checker's own version, so a copy that matches a superseded release fails before any blob is read; `.codex/hooks/loom-checker` must equal the shim `codex_scaffold.SHIM_TEMPLATE` renders for that version; `.codex/hooks/contract/<rel>` must equal `<that dir>/../contract/<rel>`; the comparison is blob **and** mode (`git show --raw` reports both, so a mode-only change fails like a content change), and a plumbing path that is a symlink at the commit (mode `120000`) is never exempt — it is gate work whatever it points at; `.loom-hook-fired` is ignored. "Two cached plugin versions": the canonical is whichever checkout the hook invoked (the hooks.json of the version Claude Code loaded), and a copy stamped with another version fails the comparison and owes a trailer. Stated residual (round 4 spec-S8): a loaded plugin that is itself a deliberately older version is its own, older canonical — loom checks no freshness against the newest cached version or the trunk's `plugin.json`; on a single-user machine this is the user downgrading their own gate, and it goes to the same follow-up intent as the Codex scaffold-commit seam. A plumbing path with no canonical counterpart (an extra file under `contract/`) fails the comparison. Recorded limitation: on Codex the scaffold refresh commit (and the first-contact scaffold commit of `write-plan` step 0b) still needs a `Task:` trailer, which is a seam of its own — it goes to a follow-up intent, not this change.
- **Test oracle for the self-check (agent-decided).** `test_the_repos_own_change_matches_its_own_review_json` (loom-code/scripts/test_loom_checker_intake.py:385-447) derives its expected block set dynamically; it gains the branch: intent status `closed …` → expected `{intake.confirmed}`. The CI failure it currently produces is kept as `evidence/ci-781-intake-confirmed.md`.
- **Contract version (agent-decided).** Stays 1.0: an added accepted value is backward compatible for every consumer requiring `>=1.0`. Plugin bumps as REQ-5.
- **Checkpoint-cost table (agent-decided).** Written by the blind-runner at branch end from `git log` and `review.json`, so the numbers are recomputed by someone who did not produce them. Recommendation only — the decision is deferred to the second and third real change (user-decided 2026-09-03).
- **Merge (user-decided 2026-09-03).** The user presses merge; the agent stops after `gh pr create`.
- **Test nits (agent-decided).** Fixed in the task that already touches each file (`test_check_mechanisms.py`: R30-O1, R30-O2 (R28-O2 moot, see REQ-6); `test_session_start_words.py`: R30-O3; `loom_checker.py`: R24-O2); R30-O2's guard asserts, via `inspect.getsource(check_mechanisms)`, that no `subprocess` call in the module names `wc`.

## Alternatives considered
- A `push` flag or waiver for docs-only commits — rejected: a declared bypass; the design has no waivers.
- A second accepted HEAD shape for `push.review-only-head` with the merge proven from the parent tree (round-1 design) — rejected: one more rule semantics and a grammar-only PR pointer; superseded by closing on the branch.
- A 28th rule for the close commit's diff shape — rejected: the recompute fits `push.review-only-head` (it already reads the tip commits' shape) and a new id would need a budget exception (PRINCIPLES.md principle 4).
- Disclosing the verdict-sha gap as a residual and deferring it (spec v5–v6) — rejected by kouko (option A, 2026-09-03) after round 5's vendor split: Codex held that institutionalising a prose-enforced round once per ship does not conform to Non-negotiable 3; the tightening closes the pre-existing gap for every post-pass commit, not only this flow.
- Closing the intent before the branch-end round with no PR number in the line (option B) — rejected by kouko: cheaper per ship, but leaves the verdict-sha gap open elsewhere.
- Writing `closed` inside the review-only commit itself — rejected: that commit may touch only review.json; the close is its own commit immediately before it.
- Exempting plumbing paths by prefix for the trailer rule (round-1 design) — rejected by the red team: it lets gate content hide under `.codex/hooks/contract/`.
- Bumping only loom-code — rejected: Acceptance #5 (user-confirmed) and both sibling plugins describe the status values in prose.
