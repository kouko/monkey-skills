## 素材

專案資料夾：使用者本機的一個私有目錄（路徑與內容不入本 repo，見下方脫敏聲明）。

**脫敏聲明**：本次的素材是使用者雇主的內部業務資料，而 `monkey-skills` 是公開 repo，
因此題目本身、產品與公司名稱、來源檔清單一律不記錄於此。以下只保留判斷 think-orbit
好不好用所必需的**結構性事實**——它們不含任何業務內容，卻足以支撐本檔的每一條發現。
需要復原細節時，素材在使用者本機，本檔的發現逐條可對照重驗。

真實題目，非演練：一份跨多份來源、需要在數條互斥路徑之間做取捨的規劃工作，
最終要產出一份可執行的流程設計。刻意採 clean-room 方式進行——一份既有的同類設計被明文隔離不讀，
理由是先讀會錨定新方案。

輸入為 10 份本機 markdown 快照，內容涵蓋使用者研究、會議紀錄、指標提案與訪談語料。

一輪坐下來的產出：

| 目錄 | 數量 |
|---|---|
| `nodes/` | 17（GOAL 1、DECISION 2、FACT 8、CLAIM 6） |
| `assumptions/` | 18 |
| `research/` | 1 |
| `views/` | `dag.md` + 2 份 `impact-*.md` |

節點 body 規模：2–4 段，161–474 個中文字元（中位數約 250）。分支 9 條，其中 `exclusive` 2、`complementary` 2、其餘 5 條的 `branch_type` 在 `views/dag.md` 上顯示為 `(?)`。

## 發現

以下五項，前四項為缺陷，第五項為推翻的假設。

### F-T12-01 — 靜默寫入扼殺了推理的 articulation（🔴 主因）

`thinking-session/SKILL.md:44` 規定「Everything else is **silent file writing**. No forms, no per-node confirmation, no progress narration」，`:66` 再加「you write silently」。實際效果不只是「不對使用者說」，而是**推理在當下根本沒有被 articulate**，因此也沒有東西可以寫進節點 body。

量測（本專案 17 個節點，檢查 body 是否用文字交代自己承接哪個 input）：

| 節點類型 | 有 `inputs` 者 | body 用文字交代關聯者 |
|---|---|---|
| DECISION（受 interrupt (c) 保護） | 2 | **2 / 2** |
| CLAIM / FACT（靜默寫入） | 8 | **0 / 8** |

分界線精準落在「該步驟有沒有觸發 interrupt」上。受打斷保護的節點之所以好讀，是因為打斷迫使一場把推理講出來的對話真的發生過；靜默產出的節點沒有這一步，body 因此是孤立陳述。

使用者原話：「think-orbit 這個 skill 完全不會跟使用者解釋當前推理的過程與邏輯以及各種決議事項，這是很嚴重的問題，這會讓整個過程的透明度變得很低（這原本是此 plugin 要解決的問題）。」

附帶因素：本 repo 使用者的全域 CLAUDE.md 要求「結論先行、不要旁白、no preamble」。該偏好與 skill 的 silent 規則疊加，agent 更無理由開口。修正時必須在 skill 內明寫本 skill 是該偏好的刻意例外。

### F-T12-02 — CLAIM/FACT 沒有承接上游的敘事義務（🔴）

`inputs: [{ref, load_bearing}]` 只記機器可讀的邊。契約沒有任何一處要求 body 用人話說明「這一步為什麼從上游推得出來」。讀者打開單一節點檔，只看到一個 id（例如 `ref: <某個上游節點的 id>`），必須另開檔案才知道那是什麼。

DECISION 節點天然滿足這項義務（見其中一個 DECISION 節點：交代被否決的替代方案、指出某個仍為 open 的假設是整條路的單點失效、說明某個上游為何刻意標成非承重），但那是 interrupt 的副產品，不是契約要求。

### F-T12-03 — 被否決的路徑沒有成為節點（🟡）

`views/dag.md` 有 4 條分支 —— 四條各自對應一個被考慮過的替代方案 —— **只裝假設，沒有任何節點**。替代方案的實質內容只存在於裁定節點的散文裡，圖上讀不到。

連帶：這些分支的 `branch_type` 顯示 `(?)`，因為 branch id 只由假設攜帶，而假設 schema 沒有 `branch_type` 欄位。

### F-T12-04 — 假設數量超過節點數量（🟡）

18 個假設 vs 17 個節點。成因是 F-T12-03 的下游效應：每個替代方案開一條分支，但分支裡只住假設，於是「每分支 ≤3」的上限被乘以分支數。整張圖讀起來像假設的展覽，而非推理的鏈。`≤3` 這個上限原本的意思是「3 個假設支撐 1 個主張」，在沒有主張節點的分支裡失去了意義。

### F-T12-05 — 推翻：節點粒度不是主因（❎ 假設被證偽）

初始判讀（含使用者的直覺）是「節點太小，導致單一文件難以理解」。實際量測後不成立：節點 body 為 161–474 中文字元、2–4 段，內容不薄。同樣被推翻的還有「shipped 的 worked example 是佔位符，所以 body 都是殘根」這條推論 —— 範例確實是佔位符（`Body text in short paragraphs.` / `Longer body text explaining the goal.` / `Optional body with more detail.`），但實際產物並未照抄。

（過程記錄：第一次量測用 `wc -w` 統計中文，得出「中位數 18 字」的錯誤結論並據此下判斷。中文無空格，`wc -w` 不適用。改以字元數重量後結論相反。）

正確歸因是 F-T12-02：問題不是尺寸，是承接義務缺席。合併節點使其變大不會讓它們開始交代關聯，只會得到更少、一樣孤立的檔案。粒度是否需要調整，應在 F-T12-01/02 修正後以真實素材重跑一次再判 —— 該順序可逆，反序不可逆。

## schema 變更

**需要變更**，因此 Part 2 brief 的 OQ-1（「檢查點是否會迫使 node schema 改動」）就此解決為「是」。變更方向（細節留待 Part 2 brainstorming 定案，此處只記檢查點認定的必要性）：

1. **node body 的必填敘事骨架** —— CLAIM/FACT 取得與 DECISION 對等的義務：承接誰（人話重述，非貼 id）／多說了什麼／什麼會讓它垮。`check` 可機械化的部分僅止於「body 是否提到至少一個 input 的 id 或其 summary 關鍵詞」，可把 0/8 推到 8/8，但擋不住敷衍 —— 品質由 F-T12-01 的修正保證，不由閘門保證。
2. **分支必須含節點** —— 開分支時每條路先寫一個 CLAIM 陳述該路的主張，假設掛在其下。連帶解決 F-T12-03 的 `branch_type: (?)` 與 F-T12-04 的假設膨脹。
3. **對話面的說話分類**（非 schema，但同屬契約）—— 流程播報禁止、推理外顯必須、打斷維持三種。三者的成本來源不同：打斷的成本是使用者的時間，推理外顯的成本近乎零，原契約把三者當一件事禁掉。

不變更：節點粒度、`≤3 假設/分支` 上限、`paragraph-form` 的 2–4 句規則。

另記一項非 schema 的增補候選：`render` 除 mermaid 圖外另產一份**線性閱讀版**（依 `seq` 串成可讀敘事）。「單一節點檔難以獨立理解」因此有第二個出口，且不動 schema 與既有專案相容性。

## Part 2 go / no-go

**GO**，由使用者裁定。

裁定內容（verbatim）：透明度的交付面「兩邊都做 討論當下看得懂，事後翻檔案也看得懂」。

此裁定的直接後果，須寫入 Part 2 契約：同一段推理會被交付兩次（一次在對話、一次在 body），因此契約必須明寫**檔案要能獨立成立，即使該推理剛剛已在對話中講過** —— 否則 agent 會因「已經講過」而把 body 寫薄，或反向省略對話。

Part 2 進入條件已滿足：OQ-1 已解，四項缺陷有量測與檔案級證據，粒度爭議已收斂為「修正後重測」而非阻塞項。
