# 記憶的時機規則要住在 skill 裡
originator: kouko
kind: engineering
needs-design: no — 這是把一條既有規則從 repo 資料搬進出貨的 skill 散文，並在審查站加一句陳述時機的話；不新增使用者要讀或輸入的介面，也沒有多狀態行為
status: confirmed 2026-09-11
publication: automatic — authorized 2026-09-11 by kouko

## Problem
記憶的「什麼時候記」有一條明確規則，寫在 `docs/loom/memory/README.md` 第 40-48 行：分支關閉前就已經知道的事實，**必須**落在同一個分支／PR，絕不另開一個合併後的分支——那是純粹的 overhead。

這條規則當初（#515，2026-07-08）不只是散文：`finishing-a-development-branch` 這支 skill 裡有五行強制指示要求收尾時就地記錄，還有一支測試釘住它。loom 1.0 硬切換（#780）砍掉那支 skill 時，**指示和測試一起消失了，只有散文留在 repo 的資料檔裡**。

現況查證下來有兩個洞，而且是不同的洞：

- **規則不跟著 plugin 走**：它躺在這個 repo 的資料檔裡。別的專案裝了 loom-workflow，讀不到它。
- **流程裡沒有那個提問點**：closing review 的 SKILL.md、reviewer／blind-runner／adversary 三份 agent 契約、11 個 code 維度、5 個 docs 維度、19 條 checker 規則——**沒有任何一處問「這個分支該記的教訓記了沒」**。記憶在審查裡目前只以「證據來源」的身分出現一次（deletion-first 允許引用一條既有 entry 來佐證）。

後果具體且已經發生兩次：#821 與 #822 的教訓都在 review 階段就浮現了（對抗探針、reviewer findings、盲跑結果），卻一路推到合併之後才想起要記，於是「記一件早就知道的事」變成要再走一輪完整流程。

## Proposed outcome
時機規則分兩半落地。判斷的那一半——什麼算耐久教訓、怎麼寫——寫進記憶 skill 自己的 Record 契約，跟著 plugin 走到任何採用它的專案。機械的那一半——「這個 repo 有沒有 store、現在是不是該記的時刻」——以一句不呼叫任何工具的話放進 closing review，落在教訓已全部浮現、attestation 尚未產生的那個窗口裡，讓記下去的東西天然被同一份 attestation 涵蓋。

## Acceptance
1. 我在任何一個裝了 loom-workflow 的專案裡讀記憶 skill，都看得到「什麼時候該記」這條規則，不需要去翻某個 repo 的儲存目錄。
2. 規則講得夠具體，讓一個沒讀過這段歷史的 agent 照著做就會在分支還開著的時候記錄，而不是事後另開 PR。
3. 那一個例外（只有合併後／安裝後才觀察得到的事實）同樣寫清楚，而且說明那種情況要批次處理，不是一個發現開一個 PR。
4. 這條規則的**兩半**——時機（分支關閉前就記）與稀少性（審查翻出來的大多不是耐久教訓）——各由一個機制守住，因為「被刪除」與「被稀釋」是兩種不同的失效：
   - **刪除**由回歸測試擋：任一半從出貨文字裡消失時測試會紅。它釘的是壓平空白後的**字面片語**——散文可以自由換行，但換掉片語用字一樣會紅。那是這個機制已知且無法消除的代價；紅了的正確反應是先確認條款還在、在同一個 commit 更新片語清單，而不是刪掉斷言。
   - **稀釋**由冷讀評測擋：一個沒讀過這段歷史的 agent，只拿到那段出貨文字與一個真實案例，照著做會在分支還開著時記錄，而且會拒掉大多數候選。
   - 那支測試本身必須**自我解釋**：它的 docstring 與失敗訊息要說明這段話為什麼在這裡（#515 建立、被 loom 1.0 連同測試一起誤刪過一次），否則下一個重構的人會把測試改綠而不是停下來問。
5. closing review 走到收斂之後、產生 attestation 之前，會讓執行者看到一段話，它同時說明兩件事：**時機**（分支關閉前就已經知道的事實現在就記，合併後另開分支是純粹的 overhead）與**稀少性**（審查翻出來的東西大多不是耐久教訓——一次性實作失誤屬於它的 commit、驗證紀錄屬於 evidence、待辦屬於 intent；通常一個 change 零到一條）。那段話不點名任何 plugin、不呼叫任何工具，只指向儲存目錄這個可以直接查證存不存在的事實。
6. 這次改動沒有讓記憶 skill 的既有行為改變：四個操作、儲存格式、驗證器都照舊；也沒有任何 loom 站台因此變成會自動呼叫記憶。

## Constraints
- 規則的內容以 `docs/loom/memory/README.md` 第 40-48 行的現行文字為準，這次不重新設計規則本身，只改變它住在哪裡、由什麼守。
- 記憶維持被動觸發：Acceptance 5 那句話只**陳述時機**，不觸發、不呼叫、不假設任何 plugin 已安裝。這是它不違反 #821 REQ-4（禁止站台因為走到該站就呼叫記憶）的理由，必須在實作時講明，否則審查會拿 REQ-4 擋。
- 那句話點的是 `docs/loom/memory/` 這個路徑，不是 plugin 名稱。契約引用規則明文豁免 loom 為採用 repo 定義的協定路徑（store 目錄算 schema，不算引用）。
- 那句話**不得**標成 `<!-- gate: <id> -->`：憲章的 Won't do 禁止只有散文的閘門，而這條規則的判準是判斷、不可機器化。沒有標記的散文不計入機制淨數，因此不需要 budget exception。
- 不新增 checker 規則。kouko 於 2026-09-11 選擇選項 A2：skill 契約 ＋ review 站一句不呼叫的提醒，以回歸測試保護，不做閘門。
- 第二廠商（Codex）這次不用——kouko 於 2026-09-11 決定，只管這個 change。
- 實作、發布到「PR 開完且 CI 全綠」為止都已授權；合併仍是另外的決定。

## Out of scope
- 讓 store 的成長速度上升：這段提醒的設計意圖是**壓低**而非抬高記錄量，因為現有的分類過濾器只管「這一條算不算」，不管「你一次想記八條這件事本身就是訊號」。
- 重新設計規則本身的內容或那個例外的範圍。
- 改變記憶的四個操作、儲存格式或驗證器。
- 讓任何 loom 站台自動呼叫記憶，或新增任何 checker 規則、prose gate。
- 在 ship 站加任何東西：那個時刻已經太遲，內容定稿後再記會讓 attestation 失效。
- 補記這個 session 累積的那些教訓（那是這個分支上順手做的事，不是它的目標）。

## Amendments
- 2026-09-11：kouko 指出審查階段浮現的多半是零散的實作失誤，加提醒可能讓 store 灌水。用這個 session 自己的資料驗證：25＋個 findings → 10 條候選 → 分流後約 8 條該進 store，而 store 現有 289 條、近三個月約每天 2 條（且是在沒有系統性提醒的情況下）。風險屬實。因此那段提醒改為同時承載時機與稀少性，Acceptance 4 的測試也要釘住兩半，避免未來只留下時機那半而讓提醒變成灌水機。
- 2026-09-11：原本只打算把規則放進記憶 skill（選項 A1）。kouko 追問後查證發現 closing review 對記憶完全沒有任何提問點，A1 因此修不了實際的失敗模式——兩次都是「沒想到」而非「想到但記錯地方」。改為 A2，並把那句提醒放在 review 站而非 ship 站，因為教訓浮現於 review、而 ship 時內容已定稿。
- 2026-09-11：查證業界實務後修訂 Acceptance 4。原文要求「一支測試」同時擋刪除與稀釋，但字串斷言在原理上測不到稀釋——保留關鍵詞的軟化改寫照樣綠。查證同時指出字串釘自身的已知失效（snapshot 疲勞：測試紅了最省力的修法是改測試），而 2026-07 那次正是這個路徑：loom 1.0 刪掉 skill，指示與測試一起消失。因此拆成兩個機制，並要求測試自我解釋。kouko 於 2026-09-11 選擇此方案（選項 B）。
- 2026-09-11：Round 2 修訂 Acceptance 4 的措辭。原文說測試「釘的是必要元素，不是整句，所以保留兩半的改寫不會誤報」——審查指出那是誇大：實際釘的是十一個字面片語，忠實改寫換掉用字就會紅，而聲稱證明這個邊界的探針只做了空白重排、沒換任何字。改為據實陳述機制的代價與紅燈時的正確反應。同時 Acceptance 5 那段話的理由被推翻並重寫：memory 條目本身就是 functional content，寫進去會改變 digest，原文「會被即將產生的 attestation 涵蓋」是假的。
