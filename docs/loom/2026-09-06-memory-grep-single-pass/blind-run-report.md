## 特別加測一項:你的 git 版本太舊的時候,這個工具現在會怎麼樣

這不是原本五條驗收項目裡的一條,但這次追加修正專門處理了這個狀況,而且是這次改動裡對使用者最直接的一項安全防護,所以我單獨拿出來完整測過。

背景是這樣:這個工具依賴 git 的一個特定功能來一次讀出所有記錄。如果使用者的 git 版本比較舊、不完全支援這個功能,舊版的修正方式可能會「表面上正常跑完、但其實什麼都沒讀到」,畫面上顯示「這段時間沒有記憶」,而實際上倉庫裡明明有一堆真實記錄 — 這是最危險的一種壞法,因為使用者看不出來哪裡不對。

我沒有直接相信這次修正的說明,而是自己動手模擬了三種不同新舊程度的 git,逐一實際跑過(以下全部在 `50b904e5` 這一版重新驗證):

- **完全支援新功能的 git(目前主流版本)**:正常走最快的路徑,結束代碼 0,資料完整,跟平常一樣。
- **支援一部分、但不支援最新那個篩選寫法的 git**:工具會自動偵測到這件事,改用一個舊一點但雙方都支援的寫法重新讀一次(多花一次呼叫,但只多這一次,不會變慢很多),資料一樣完整,結束代碼一樣是 0。我逐字比對了這種情況跟正常情況的輸出,完全一樣。
- **連那個舊一點的寫法都不支援的 git**:工具會直接停下,不會假裝正常跑完,結束代碼變成 3,並且印出清楚的訊息告訴使用者是哪個功能不支援、建議升級 git 到哪個版本以上再試。我實際跑了這個情境,確認訊息內容清楚可讀、結束代碼確實是 3。

另外我還多測了一種情況:如果某一筆記錄的內容裡剛好「引用」了跟這個 git 功能長得很像的一段文字(例如有人在筆記裡貼了一段程式碼片段,恰好長得像這個功能的寫法),工具會不會誤判成「這台 git 太舊」而錯誤地放棄讀取?我實際造了這種記錄去測,結果工具正確地把它當成普通的文字內容處理,沒有誤判 —— 而且這一點在 `50b904e5` 這一版又更進一步了:判斷「這台 git 支不支援」的這個問題,現在完全不去看倉庫裡任何一筆真實的進版紀錄,而是靠工具自己臨時生出來的一份樣本去問,所以不管你或任何人在進版紀錄裡寫了什麼字,都不可能把工具誤導成「拒絕執行」或「走比較慢的路徑」。

- **證據**：我自己動手模擬三種 git 的過程,以及那個「引用文字誤判」測試用小倉庫,任何人都可以照做重跑;這次改動也內附了針對前兩種 git 情境寫死的重跑測試:`python3 -m pytest docs/loom/2026-09-06-memory-grep-single-pass/evidence/probes/test_abuse_memory_grep_branch_end.py -q -k "test_extract_commits_incompatible_git_rejects_loudly or test_extract_commits_incompatible_git_literal_placeholder_not_silently_dropped"`(我實測 2 個全部通過)。

**判定**:這項安全防護做到了,而且我用自己造的模擬環境獨立驗證過,不是只看說明照抄。

  5. **審查紀錄裡有一個內部統計數字(不是這個工具的行為,是審查過程自己記錄的一個計數)看起來對不上**— 這件事不是我負責修的,也不影響你使用這個工具的方式,我看了一下目前的記錄,數字已經對得上了,但這不是我驗證過的範圍,所以我不敢在這裡替它打包票。

## 未解的問題

- **一個跟這次改動無關、但我測試時剛好碰到、你應該知道的舊毛病**:如果對著一個完全沒有任何一筆進版紀錄的全新倉庫執行這個工具,它會直接當機式地丟出 git 自己的原始錯誤訊息並以一個沒有在工具說明書上列出的代碼結束(工具自己的說明書只列了幾種正式的結束代碼,這個不在其中)。我在最新版本上重新試了一次,確認**這個狀況目前還是一樣**,行為跟改動前一模一樣,所以確定不是這次改動造成的,是本來就存在的狀況;但既然使用者可能真的會在初次建立、還沒有任何紀錄的倉庫上跑到這個工具,我認為值得讓你知道這件事,以後有空可以決定要不要補上說明或修掉。
- **前面提過的「最低 git 版本沒有查證過」的殘留部分** — 現在就算 git 太舊,工具至少會清楚報錯而不是給空結果,這部分風險已經因為這次追加修正而降低很多。但「到底多舊的 git 算太舊」這件事,我在這台機器上還是沒辦法進一步查證(沒有離線資料、也沒有連網去查),只能提醒你:如果團隊裡有人的環境比較舊,遇到問題時工具至少會告訴他升級,不會再悶不吭聲。
