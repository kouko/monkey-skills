## 特別加測一項:你的 git 版本太舊的時候,這個工具現在會怎麼樣

這不是原本五條驗收項目裡的一條,但這次追加修正專門處理了這個狀況,而且是這次改動裡對使用者最直接的一項安全防護,所以我單獨拿出來完整測過。

背景是這樣:這個工具依賴 git 的一個特定功能來一次讀出所有記錄。如果使用者的 git 版本比較舊、不完全支援這個功能,舊版的修正方式可能會「表面上正常跑完、但其實什麼都沒讀到」,畫面上顯示「這段時間沒有記憶」,而實際上倉庫裡明明有一堆真實記錄 — 這是最危險的一種壞法,因為使用者看不出來哪裡不對。

我沒有直接相信這次修正的說明,而是自己動手模擬了三種不同新舊程度的 git,逐一實際跑過:

- **完全支援新功能的 git(目前主流版本)**:正常走最快的路徑,結束代碼 0,資料完整,跟平常一樣。
- **支援一部分、但不支援最新那個篩選寫法的 git**:工具會自動偵測到這件事,改用一個舊一點但雙方都支援的寫法重新讀一次(多花一次呼叫,但只多這一次,不會變慢很多),資料一樣完整,結束代碼一樣是 0。我逐字比對了這種情況跟正常情況的輸出,完全一樣。
- **連那個舊一點的寫法都不支援的 git**:工具會直接停下,不會假裝正常跑完,結束代碼變成 3,並且印出清楚的訊息告訴使用者是哪個功能不支援、建議升級 git 到哪個版本以上再試。我實際跑了這個情境,確認訊息內容清楚可讀、結束代碼確實是 3。

另外我還多測了一種情況:如果某一筆記錄的內容裡剛好「引用」了跟這個 git 功能長得很像的一段文字(例如有人在筆記裡貼了一段程式碼片段,恰好長得像這個功能的寫法),工具會不會誤判成「這台 git 太舊」而錯誤地放棄讀取?我實際造了這種記錄去測,結果工具正確地把它當成普通的文字內容處理,沒有誤判。

**判定**:這項安全防護做到了,而且我用自己造的模擬環境獨立驗證過,不是只看說明照抄。

## 我替你決定的事

- **用「空字元」當作切分欄位的記號** — 舊版工具原本用一個看得見的符號當分隔線,如果標題或內容裡剛好出現那個符號,可能會把一整筆記錄切錯。新工具改用一個永遠不會出現在文字內容裡的「空字元」來切分,所以現在標題、決定、心得、注意事項裡不管出現什麼字元(包括我測到的那個藏起來的控制字元),都能完整保留、不會被誤切。以後如果要換掉這個做法,影響範圍是整支工具的欄位讀取邏輯,不是小改。
- **版本號跳的是「小版號」(4.0.1→4.1.0),不是「修補號」** — 雖然使用者打的指令、看到的畫面幾乎都沒變,但這次改動把「最低需要的 git 版本」提高了,所以照規矩用小版號跳升來提醒:如果你的環境裝的是很舊的 git,可能需要先確認能不能用。
- **檔頭寫的「最低 git 版本」是用推算的,沒有實際查證過** — 工具需要 git 提供的一個特定功能,寫檔頭的人在這台機器上(裝的是新版 git)驗證這個功能存在且可用,但這台機器沒有離線的資料能查到「這個功能是從哪一個 git 版本開始有的」,所以檔頭寫的版本號是沿用當初立案時假設的下限,不是逐版驗證過的。實際影響是:如果你或你的同事在一台裝了很舊版 git(粗估落在某個門檻以下)的機器上跑這個工具,現在至少不會再「表面正常但資料是空的」— 前面那項特別加測已經確認,太舊的 git 現在會直接停下並清楚報錯,而不是繼續給你一份看起來正常、其實內容是空的結果。但這台機器上還是沒辦法幫你確認「到底多舊算太舊」,只能等真的遇到才知道。
- **三種驗證模式(`--verify`、`--verify-merged`、`--verify-strict`)這次完全沒有動** — 這三個模式本來就很快(量測起來是零點零幾秒等級),所以這次改動特意不去碰它們,把力氣花在真正慢的那三千次子程式呼叫上。我核對過這三個模式對應的程式碼區塊,改動前後逐字相同。
- **這一項是你自己拍板的,不是我替你決定的**:上一輪我把「有一筆真實記錄舊工具漏讀、新工具讀得比較全」這件事當成一個未解問題回報給你,你看過之後親自核准了一個例外規則 — 只要點名是哪一筆記錄、多讀到幾行,這種「漏讀被順便修好」的差異算通過。我這次重新驗證,確認差異確實只出在你核准的那一筆(2026-08-28 那次規則修正),多讀到的行數確實是 4 行,而且六組用法的結束代碼全部一致。我把它記在這裡,是為了讓你在讀這份報告時知道:這一條例外是你自己看過內容之後決定的,不是我自己判斷通過的。
- **沒有任何「重要」以上等級的審查意見被擱置不修** — 我看了審查紀錄,審查抓到的問題(含前面提到的「標題藏控制字元會漏記錄」、以及後來追加審查抓到的「舊 git 表面正常但資料是空的」這兩個嚴重問題)全部在同一個分支裡修完了,審查最後給了全部通過、零問題的結論。也就是說沒有「這個問題我們知道但決定先不修」的狀況。
